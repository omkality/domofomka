# Работа с domofomka

## Границы проекта

- Локальная разработка выполняется в этом репозитории, без дополнительных worktree и копий исходников.
- Бот — `src/vkbot`; сервис кодов — `src/code_service`; общие технические компоненты — `src/infrastructure`.
- HTTP-приложение собирается в `src/code_service/main.py`. Маршруты находятся в
  `api/routes/v1` и `api/routes/v2`, сценарии и читатели — в `services/v1` и `services/v2`.
  Сервисы не импортируют HTTP-обработчики. Бот вызывает сервис кодов по HTTP.
- SQL-схемы PostgreSQL меняются отдельными yoyo-миграциями с явными зависимостями и SQL отката.
  Приложения проверяют подготовленную схему, а не выполняют DDL при запуске worker.
- Подготовка данных и эксперименты находятся в `tools`; они не импортируются приложениями.

## Документация — часть изменения

После каждого изменения поведения, архитектуры, маршрутов, схемы БД, настроек,
команд или структуры репозитория:

1. Просмотреть затронутые статьи в `docs/src/content/docs` и модель `docs/architecture`.
2. Обновить описание и соответствующие схемы в том же изменении, что и код.
3. Проверить ссылки из README и примеров запуска.
4. Выполнить `cd docs && npm run build`. Проверка LikeC4, внутренних ссылок,
   якорей и размера сайта входит в сборку и CI.

Если изменение не влияет на описание проекта, явно сообщить, что документация
просмотрена и обновление содержания не требуется.

Рабочие статьи и README описывают только реализованное состояние текущей ветки.
Аудиты, сравнения библиотек, замеры, планы и историю хранить в `research`,
не смешивая их с инструкциями. Для всего процесса достаточно двух сквозных
пошаговых схем; дополнительные проекции архитектуры и БД остаются статическими.
На сайте использовать уже подключённый LikeC4; новый формат диаграмм добавлять
только при обоснованной необходимости.

Astro собирает сайт из Markdown/MDX и модели LikeC4. Он не восстанавливает описание
бизнес-логики из Python автоматически: соответствие коду поддерживает разработчик.
Документация проверяется и сохраняется отдельным артефактом CI; локальный
контейнер просмотра не является обязательным сервисом бота.

## Проверки и публикация

- Зависимости и проверки запускать через `uv.lock`: `uv sync --frozen --all-groups`.
- Перед публикацией выполнить pre-commit и тесты. SQL-интеграциям нужен отдельный
  PostgreSQL из `TEST_QUEUE_DATABASE_URL`, без доступа к рабочим данным.
- Общие фикстуры находятся в `tests/fixtures`; unit и integration разделены по фактическим границам.
- Токены, DSN, переписки, дампы и построчные данные не публиковать. `.env` и `artifacts` остаются вне Git.
- Изменения сначала проверяются на dev. Коммитить и отправлять ветки в рамках
  разрешения текущей задачи; master и prod менять только при явном разрешении владельца.
- Повторяемое развёртывание идёт через GitHub Actions по SHA и digest.
  Исходники на VDS вручную не подменять. Учитывать малую память и диск серверов.
- Amnezia, SSH-доступ и сторонние сервисы сохранять. Очистка Docker — только
  по проверенному списку ресурсов; глобальный prune не использовать.
