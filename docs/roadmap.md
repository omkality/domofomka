# Ближайшие работы dev

Работа ведётся на `dev` и тестовом боте. Прод и `master` сохраняются без изменений.
Ограничение архитектуры — существующие небольшие VDS, частично занятые VPN и другими сервисами.
Постоянный OpenSearch на них не планируется: рабочий v2 читает отдельную БД существующего PostgreSQL.
Локальный OpenSearch остаётся инструментом сравнения качества.

Приоритеты issues задаются лейблами по принятому в `omkalitycraft` оформлению:
`priority:P0` — аварийные исправления, `priority:P1` — ближайшие необходимые работы,
`priority:P2` — следующий этап. Внутри одного приоритета порядок задают зависимости задач.

## 1. Учёт запросов и этапов — P1, выполнено

[Задача #1](https://github.com/omkality/domofomka/issues/1), `priority:P1`.

Сначала получить достоверную картину задержек и результатов на dev. Использовать существующий PostgreSQL,
не добавляя постоянные сервисы. Связывать входящее событие, каждую попытку обработки, поиски v1/v2,
маршруты через РФ и напрямую, подготовленные исходящие действия и подтверждения VK.

Отдельно учитывать кеш, ожидания очереди, лимит частоты, паузы повторов, отложенную геолокацию,
отмену новым запросом, устаревшие кнопки и частичную доставку нескольких сообщений.
Успех поиска не означает правильность адреса, а принятие ответа VK не означает прочтение пользователем.

Ограничить размер измерений в памяти, диагностического пакета и срок хранения настройками `.env`.
Неполную диагностику обозначать явно; исторические времена не восстанавливать предположениями.
После тестов с настоящим PostgreSQL проверить накладные расходы и развернуть только на Германии.

## 2. Административные формулировки и подтверждённые дубли — P1, выполнено

[Задача #2](https://github.com/omkality/domofomka/issues/2), `priority:P1`, после базового учёта #1.

Перед закреплением хранилища сравнить локально нормализованный PostgreSQL с файловым каталогом:
место с индексами, память при лимите существующего VDS, холодные и повторные запросы, сохранность результатов.
Решение по SQLite не окончательное. Если PostgreSQL закрывает задачи в этих лимитах,
не поддерживать отдельную копию тех же нормализованных кодов без необходимости.
Полный ГАР и совместимость v1 оценивать отдельно от небольшого набора домов с кодами.

Локальное [сравнение хранилищ](storage-comparison.md) сохранило все 46 611 ответов.
Ограниченный клиент, перенос PostgreSQL на Германию и совместная нагрузка с очередью
выполнены: [отчёт](postgres-dev-2026-11-06.md). Рабочая SQLite-копия v2 с VDS удалена.

Исправить воспроизводимый пропуск длинного адреса с областью, округом и посёлком городского типа.
Не терять ограничения по населённому пункту и номеру дома.
Продолжать безопасную привязку к ГАР и объединение подтверждённых копий с сохранением происхождения кодов.
Исходная база v1 сохраняется; редактирование рабочего каталога — отдельный будущий этап.

Проверять на ручной разметке, отрицательных примерах и корпусе совместимости.
Данные, использованные для исправлений, больше не объявлять независимой проверкой.

Первая часть выполнена: исправление длинного адреса и подтверждённые муниципальные привязки
работают на немецком dev. Ещё 2 582 исходные строки связаны с ГАР; непривязанные и неоднозначные
данные по-прежнему сохраняются отдельно. Источник v1 не изменён.

## 3. Эксплуатационные проверки — P2

По измерениям выбрать воспроизводимую нагрузку: холодный кеш, разные запросы, повторные нажатия,
сетевые сбои и длительная работа. Проверить память, место, очередь и обслуживание аналитики.
Проверить аварийный запуск на одном сервере с пустыми `VK_PROXY_URL` и `DADATA_PROXY_URL`:
прямые обращения без ожидания прокси. Отдельный переключатель `USE_PROXY` пока не требуется.
По решению владельца внешние оповещения и регулярные копии на ПК не добавляются.
Системные лимиты журналов, аварийный резерв и ограниченные серверные копии описаны в [политике хранения](storage-safety.md).

Ближайшие дома по расстоянию отложены до появления достоверных координат.
Добавление новых кодов и основная редактируемая база PostgreSQL — отдельный этап после стабилизации поиска.
