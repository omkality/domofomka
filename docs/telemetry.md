# Измерения запросов на dev

Задача: [#1](https://github.com/omkality/domofomka/issues/1). Новых постоянных сервисов нет.
API измеряет операции в памяти и только по внутреннему запросу `observe=true` возвращает пакет боту.
Бот связывает его со своей попыткой и записывает в существующий PostgreSQL. Пакет не попадает в кеш результатов.
Обычные ответы API без `observe` сохраняют прежний формат.

## Какие данные сохраняются

- `request_log`: событие, псевдоним пользователя, ограниченный текст запроса, время получения, окружение,
  версия кода, общий исход и состояние полноты диагностики. Псевдоним не является анонимизацией.
- `request_spans`: каждое измеренное действие с длительностью, родительским этапом, ID задания,
  номером попытки, сервисом, экземпляром процесса и безопасным типом ошибки. Полный текст исключений не сохраняется.
- `search_runs`: каждый фактический запуск v1/v2, его результат, длительность через связанный этап,
  нормализованный запрос и снимок адресов-кандидатов без кодов.
- `network_attempts`: обращения к VK и DaData, операция, фактический маршрут, причина его выбора,
  HTTP-статус, код ошибки сервиса и действовавшие ограничения времени.

Представление `request_summary` показывает `v1_executed`, `v2_executed`, `v1_result`, `v2_result`,
суммарные времена каждого поисковика по попыткам, источник итогового ответа и fallback.
При отсутствии запуска результат и длительность остаются `NULL`, а не нулём.
Все попытки сохраняются отдельно; последняя не затирает предыдущие.

В `outcome` сохраняются кеш, причины решений, связи с выбранным адресом/подъездом,
состояние inbox и количество исходящих действий по состояниям. Несколько сообщений могут быть доставлены частично.
Подтверждение нажатия, временное предупреждение о геолокации и выдача кода — разные действия.
Нажатия связываются с исходным запросом через сохранённый контекст; при отсутствии старого контекста связь не выдумывается.
Отложенная геолокация получает отдельную запись со ссылкой на исходную.

## Этапы и интерпретация

Измеряются обработка inbox, вызов API, геокодирование, нормализация, подбор/ранжирование кандидатов,
чтение кодов, v1, создание outbox, его доставка и завершение, ожидание ограничителя VK и паузы HTTP-повторов.
У v1 отдельно видны индекс, проверка совместимости индекса, подбор с прежним сопоставлением и чтение кодов;
при недоступном индексе измеряется прежний просмотр базы. Подбор и сопоставление объединены,
чтобы ради измерений не материализовать большие наборы строк в памяти.

Начало первого `inbox.process` относительно получения события показывает ожидание обработки.
`received_at`, время допустимой следующей попытки и начала каждой попытки сохраняются отдельно.
Полное ожидание пользователя включает очереди и повторные попытки, а не только работу API.
Вложенные времена нельзя складывать: `api.lookup` уже включает удалённую обработку API.
Длительности операций считаются монотонными часами; временные отметки сохраняются в UTC.

При попадании в кеш новые `search_runs` не создаются. Источник сохранённого результата остаётся известен,
но старые измерения поиска не копируются. Обращение к сохранённому контексту кнопки также не считается новым поиском.
Принятие ответа VK не доказывает ни прочтение, ни правильность адреса.
Таймаут после отправки может означать неизвестное подтверждение доставки — это отражается отдельно.

У сетевого и поискового fallback разные признаки. Ошибка соединения с прокси и последующий прямой запрос
сохраняются разными попытками. При известной недоступности прокси первая попытка сразу бывает прямой.
Чтение ответа с таймаутом не считается доказательством недоступности прокси.
Политика безопасных повторов VK не меняется ради измерений.

## Ресурсы и срок хранения

В `.env`:

```dotenv
TELEMETRY_ENABLED=true
TELEMETRY_MAX_SPANS=128
TELEMETRY_MAX_PACKET_BYTES=65536
TELEMETRY_QUERY_MAX_CHARS=2000
TELEMETRY_RETENTION_DAYS=30
TELEMETRY_MAX_STORAGE_BYTES=33554432
TELEMETRY_DB_TIMEOUT_MS=500
APP_REVISION=release-commit
CATALOG_REVISION=catalog-sha256
```

Размер пакета и число этапов ограничены; обрезанная диагностика помечается `partial`.
Длинный исходный запрос сохраняется с признаком обрезки и хешем полного текста.
`TELEMETRY_MAX_STORAGE_BYTES` — консервативный бюджет живых диагностических записей с запасом на строки и индексы,
а не обещание точного физического размера файлов PostgreSQL. Физический размер отображается отдельно.
При исчерпании бюджета новые подробности пропускаются со счётчиком и предупреждением; доставка продолжает работать.
Очистка по сроку хранения освобождает бюджет; PostgreSQL может повторно использовать страницы без уменьшения файла.

Очистка выполняется ограниченными порциями. Активные запросы сохраняются; связи измерений не зависят от FK на inbox/outbox,
поэтому очистка завершённой рабочей очереди не удаляет аналитику раньше её срока.
Подробная диагностика имеет один срок хранения; отдельные долговременные суточные агрегаты пока не создаются.

Первичная запись события сохраняется вместе с inbox через SAVEPOINT и ограниченный таймаут SQL.
Измеренные обработчики сохраняют подробности и итоговую сводку одним пакетом после операции;
остальные изменения состояния фиксируются при изменении очереди. Пропущенную после аварии сводку
обслуживание сверяет с очередью, помечая диагностику неполной. Сбой аналитики не отменяет ответ.
Сбой процесса или БД может оставить неполные измерения: гарантии сохранения очереди сильнее, чем гарантии таймингов.
Пропуски не заменяются нулями. Тексты запросов остаются закрытыми, коды и секреты в пакеты не копируются.

## Просмотр

```bash
docker compose -p domofomka-dev --env-file .env.dev -f docker-compose.yml exec -T vkbot uv run --frozen python -m src.vkbot.manage telemetry
```

Команда выводит агрегаты без текстов и идентификаторов пользователей: результаты v1/v2, задержки,
маршруты и ошибки, физический размер и занятый бюджет. Для подробного закрытого анализа доступны четыре таблицы
и `request_summary`. Доступ к PostgreSQL наружу не публикуется.

Старые завершённые запросы не получают выдуманные времена: измерения начинаются после включения.
Контрольные синтетические события помечаются отдельным источником и изолируются от обычной статистики.

## Проверка реализации 6 ноября 2026

В Linux с настоящим PostgreSQL прошли 241 тест; одна архивная проверка пропущена.
Проверены реальные HTTP-маршруты, кеш без повторного поиска, ошибка v2 с результатом v1,
пакет ошибки геокодирования, сетевые переключения, частичная и отменённая доставка,
сохранение связей после очистки очереди, SQL-таймаут аналитики, срок хранения и ограничения размера.

Локальный чередующийся HTTP-профиль: по 60 запросов с измерениями и без них, пять фиксированных запросов,
ответы совпали во всех 60 парах. На прогретом кеше p50 составил 1,790 / 1,891 мс,
без кеша — 30,771 / 29,792 мс; p95 без кеша — 559,824 / 567,636 мс.
Разница порядка шума измерений не доказывает ускорения. Максимальный пакет без кеша — 3 948 байт.
Это проверка сбора и передачи пакета на ПК, без записи PostgreSQL и без внешнего VK; она не заменяет проверку VDS.
Закрытые журналы: `.codex-local/telemetry-linux-final.log`, `profile-telemetry-http.log`, `profile-telemetry-uncached.log`.

На Германии выполнен сквозной синтетический сценарий только для владельца: настоящий поиск,
отправка адреса и редактирование для подъезда. Оба события получили измерения и подтверждение VK;
нажатие связано с исходным запросом, коды и исходные сетевые секреты в аналитике отсутствуют.
Это проверка синтетического задания через SDK, а не имитация реального клика в браузере.
Тестовые записи изолированы от рабочего сообщества и после проверки удалены.

Первый поиск после перезапуска занял 6 111 мс; следующие четыре запроса без кеша — 23–26 мс внутри v2.
Измерение подтверждает задержку первого запроса, но не устанавливает её точную причину.
У последующих запросов подбор адресов с кодами занял 21–23 мс, остальная обработка — единицы миллисекунд.

Отдельно измерен синтетический SQL-цикл очереди без обращений к VK и DaData: по 20 чередующихся образцов.
В первой реализации p50 без аналитики / с ней — 95,880 / 213,100 мс.
После пакетной вставки этапов и устранения повторных обновлений сводки — 97,896 / 156,898 мс.
Это около 59 мс дополнительных затрат на весь проверочный цикл; существенная часть выполняется после операции.
Фоновая нагрузка VDS меняется, поэтому это ориентир накладных расходов, а не гарантия задержки.
Бюджеты памяти контейнеров остаются прежними. После первого развёртывания API/бот/PostgreSQL занимали
около 75/41/54 МиБ, свободно было около 1,3 ГиБ диска.
