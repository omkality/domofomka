## Связанные сценарии на установленном образе

Использовались настоящий внутренний API dev и отдельная временная БД PostgreSQL.
Вызовы отправки, редактирования и подтверждения кнопок VK заменены тестовым получателем.
Рабочая очередь и пользователи dev не участвовали в искусственных событиях.

1. **Единственный подъезд → потеря подтверждения отправки → восстановление runtime.**
   Повтор использует тот же `random_id`; у тестового получателя одна логическая отправка.
   Коды появляются сразу, повторная обработка фиксируется в диагностике как выдача кода.
2. **Поток запросов → другой пользователь → исправленный адрес.**
   Второй пользователь обслуживается со своим бюджетом. Из лишних ожидающих запросов
   первого сохраняется последний; одинаковая подсказка не дублируется, коды не подавляются.
3. **Выбор адреса → код → ранний возврат → таймаут редактирования → восстановление.**
   Раннее нажатие получает «Подождите…». Во время ожидающего редактирования все шесть
   видов callback-кнопок подавляются общим ограничителем пользователя.
   После пересоздания объектов runtime/processor действие восстанавливается из БД;
   список открывается только после подтверждения редактирования.
4. **Страница адресов → дом с несколькими подъездами → страница подъездов → код → возврат → отказ.**
   Сохранена исходная страница адресов. Бюджет кнопок не превышен: максимум девять
   в этих сценариях. Запоздалое нажатие после отказа не открывает меню и не вызывает поиск.
5. **Таймаут геопоиска → немедленный текст.**
   Создаётся отложенный повтор геолокации; новый текст его заменяет и обрабатывается.

Для страниц меню использовался искусственный список из 12 вариантов с настоящими ID
двух домов каталога. Он проверяет навигацию, а не качество ранжирования такого списка.
Проверка восстановления пересоздаёт runtime/processor с той же БД, не перезапускает
рабочие контейнеры. Всего выполнено десять чтений внутреннего API; шесть логических
отправок и девять редактирований были только в тестовом получателе.
В конце незавершённых заданий нет, временная БД удалена.

## Готовность первого переноса на prod

Финляндия проверена только чтением: v1.5.6 работает, 23 из 23 файлов совпадают
со снимком для отката, перезапусков и OOM нет. Свободно около 30,6 ГиБ диска и
517 МиБ доступной памяти в момент проверки. Таймер защиты диска активен.

Принятый дамп каталога существует, его SHA-256 совпадает с манифестом:
`b37c9b12878b939024d70cdafc97710a7386e570b20c4db3a4a050ffdd375c4e`.
Размер — 332 907 810 байт. Ранее проверенное восстановление и сравнение таблиц
остаются действительными: каталог в этом цикле не изменялся.

Остались действия первого выпуска, выполняемые после команды владельца:

1. Установить prod-приёмник из опубликованного Git-комплекта и **до изменения `.env`**
   заморозить исходники, окружение и образы v1.5.6 для отката. Сейчас prod-приёмник ещё не установлен.
2. Подготовить PostgreSQL, перенести принятый каталог и индекс v1, проверить таблицы,
   права читателя и лимиты ресурсов. Очередь prod создаётся отдельно; тестовые задания не переносятся.
3. Подготовить `.env` рабочего сообщества и секреты GitHub Environment `prod`.
   Сейчас этот Environment создан, но секретов в нём нет; `PROD_DEPLOY_ENABLED=false`.
4. Слить PR в master, собрать образы его ревизии и выполнить prod-workflow.
   Проверить поиск, геометку, автоматический код, кнопки, очередь и ресурсы;
   зафиксировать выпуск v2.0.0. Сохранить возможность отката до принятия первого выпуска.

Подробности — в [плане выпуска и отката](release-v2.md). Дополнительные объединения
адресных записей из задачи #12 не входят в этот выпуск и не смешиваются с принятым каталогом.
