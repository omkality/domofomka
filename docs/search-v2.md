# Поиск v2: устройство, данные и результаты проверок

Текущее хранилище dev — PostgreSQL. См. [схему БД](database.md) и [проверки переноса](postgres-dev-2026-11-06.md).
Описание файлового каталога ниже сохраняет историю подготовки и сравнения данных.

## Область изменений

Последующие результаты разметки, нормализации и ускорения v1 описаны в
[проверках следующего этапа](development-checks-2026-11-06.md). Числа исходных прогонов ниже сохранены как история.

Изменены только ветка `dev` и тестовый бот TEST ASYNC DOMOFOMKA. При этих работах прод остался на v1.5.6.
Исходная `codes.db` используется только для чтения и совместимости. Исходные строки не удаляются.
Переписки VK, разметка запросов, файлы ГАР и созданные базы находятся в игнорируемой папке `artifacts/`.
При массовой нормализации не используются ИИ-модели и платные запросы очистки адресов.

## Подготовка данных

1. `python -m tools.import_gar --regions all --workers 5` потоково читает уже распакованный XML ГАР.
   Каждый процесс обрабатывает базу одного региона. Сохраняются только актуальные и действующие адресные объекты и дома.
   Адрес восстанавливается по административной иерархии; квартиры, комнаты, участки и сведения о владельцах не загружаются.
   Города областного значения на уровне 2 распознаются по типу объекта; уровни 5/6 позволяют сохранить вложенные города и населённые пункты.
   Районы и городские округа не подставляются вместо города. Готовый регион отмечается версией схемы; отдельный неудачный импорт можно повторить.
2. `python -m tools.build_catalog` создаёт новый каталог рядом с действующим.
   Дома сохраняют GUID ГАР. Коды привязываются только при однозначном совпадении населённого пункта, улицы, типа объекта и дома.
   Для исходных вариантов адресов создаётся отдельный полнотекстовый индекс; идентификатор каждой исходной строки сохраняется в `provenance`.
   При повторной привязке перестраиваются индексы улиц и вариантов написания, поэтому неподтверждённые исходные адреса не исчезают из поиска.
   Различия регистра, Unicode и формата записи могут объединяться. Одинаковые улица и дом в разных городах сами по себе не являются дублями.
   Неоднозначные и непривязанные адреса остаются отдельными неподтверждёнными записями старой базы.
3. `python -m tools.compact_catalog` создаёт рабочий каталог для сервера — около 787 МиБ.
   В нём находятся ключи известных домов, записи домов с кодами и исходные варианты адресов.
   Команда `python -m tools.build_catalog --refresh-keys-only` обновляет ключи после изменения нормализации. Её выполняют на отдельной сборке; затем заново создают компактный каталог и индекс поиска.
   Документы улиц отделены от домов и строк кодов. В OpenSearch индексируется одна улица в населённом пункте с точными ключами домов, а не копия полного адреса для каждого кода.
   `python -m tools.index_search` создаёт новый индекс, проверяет количество документов и атомарно переключает поисковый псевдоним.
   Прежние индексы остаются для отката: скрипт не удаляет существующий рабочий индекс.

## Сценарии запросов

- `/codes/*` и `/api/v1/codes/*` сохраняют прежнюю логику поиска.
- `/api/v2/codes/msg` разбирает сведения о подъезде и квартире, сокращения городов, порядковые номера улиц и части номера дома.
  OpenSearch, если он подключён, добавляет кандидатов к результатам индекса каталога.
  Дом, корпус и строение проверяются точно; дополнительная проверка сопоставляет слова запроса с адресом.
  При недоступности OpenSearch используется индекс каталога со словарём улиц и ограниченным исправлением опечаток.
- Дом найден, коды есть: бот присылает адрес с кнопками подъездов. Код показывается редактированием того же сообщения.
- Дом найден, строк кодов нет: бот показывает адрес и сообщает, что кодов в базе пока нет.
  Это не утверждение об отсутствии домофона или кода у самого дома.
- Подходит один адрес с кодами: он открывается сразу. Подходят несколько: бот предлагает только варианты с кодами и сохраняет список вместе с сообщением.
  Выбор не может сослаться на постороннего кандидата. После выбора то же сообщение получает кнопки подъездов; следующее нажатие показывает коды.
  Для домов с числом подъездов больше десяти дополнительные группы кнопок приходят отдельными сообщениями, как в v1.
  На каждой странице есть «Ни один не подходит»: клавиатура убирается, то же сообщение просит прислать полный адрес одним сообщением.
  Несколько совпадений без кодов не создают меню; бот просит уточнить полный адрес.
  Если номер дома не указан, порядковый номер улицы не подставляется вместо него: «третий Покровский проезд» требует номера дома.
- v2 не нашёл адрес или каталог недоступен: выполняется прежний поиск v1 — резервный вариант, далее `fallback`.
  Уже распознанный дом без кодов и неоднозначный результат не заменяются другим домом из v1.
- Геометка: DaData определяет адрес, затем v2 ищет его в каталоге.
  При временном отказе бот сохраняет отложенный повтор и предлагает прислать текст. Новое сообщение отменяет старую геолокацию.
- Повторные нажатия, таймаут отправки или редактирования, перезапуск: журналы inbox/outbox в PostgreSQL и постоянные идентификаторы отправки сохраняют работу и подавляют дубли.
  Нажатия, которых бот не получил от VK, в истории сообщений отсутствуют и не восстанавливаются.
- Компьютер разработчика выключен: немецкий тестовый бот продолжает работать со своим компактным каталогом.
  Туннель к ПК не нужен. Кандидаты OpenSearch всегда объединяются с кандидатами каталога перед окончательной проверкой.

## Кэш и сохранность запросов

Для v1 есть отдельный необязательный `LEGACY_INDEX_PATH`. Он ускоряет отбор кандидатов, сохраняя прежние проверки,
порядок строк и повторы кодов. Команда `python -m tools.build_legacy_index` создаёт индекс рядом с исходной базой.
Перед использованием проверяется хеш `codes.db`; при несовпадении или отсутствии индекса выполняется прежний просмотр базы.
Сам v1 сохраняет поведение. В v2 резервный ответ дополнительно проверяется на совпадение указанного номера дома.

Redis больше не нужен для контекста кнопок и ограничения нажатий: это состояние хранится в PostgreSQL вместе с очередью.
Индекс каталога ускоряет первый поиск, но не заменяет кэш результатов.
Повторные текстовые запросы v2 и геозапросы используют небольшой LRU-кэш в каждом процессе API.
По умолчанию срок жизни — 120 секунд, максимум 256 записей и 2 МиБ сериализованных данных и ключей.
Объекты Python занимают дополнительную память; жёсткий лимит контейнера остаётся отдельной защитой.
При нескольких процессах у каждого свой лимит и свой кэш. Одновременные первые запросы могут выполнить поиск независимо.

`SEARCH_CACHE_TTL_SECONDS=0` выключает кэш. Остальные параметры — `SEARCH_CACHE_MAX_ENTRIES` и `SEARCH_CACHE_MAX_BYTES`.
Слишком большой ответ не сохраняется. Исключения и ответ с причиной `unavailable` не кэшируются.
Ключ включает версию файлов каталога и исходной базы, параметры поиска и исходный запрос.
После атомарной замены каталога старые результаты не выдаются; содержимое прежних записей вытесняется в пределах лимита.
Смена индекса под тем же псевдонимом OpenSearch может стать видна после TTL; для немедленного обновления перезапустите API.
Геокоординаты не округляются: соседняя точка не получает результат другой точки только ради попадания в кэш.
Кэш не заменяет журналы PostgreSQL и полностью теряется при перезапуске без потери заданий.

При отдельном замере на ПК с настоящим каталогом и OpenSearch первый поиск занял 288,160 мс,
медиана 11 повторов с попаданием в кэш — 0,358 мс. Это время вызова поиска, без HTTP-доставки и VK.

## Аудит переписок и проверка качества

`python -m tools.export_vk --env <private-env> --output artifacts/private/vk-prod`
читает историю личных диалогов, доступную API, по сохранённому списку диалогов. Выгрузка не отмечает сообщения прочитанными и ничего не отправляет.
Порции истории запрашиваются с ограничением частоты; ограничения VK и серверные ошибки вызывают паузу с увеличением задержки.
При возобновлении уже выгруженные диалоги не загружаются заново. Набор сохраняемых полей ограничен; списки профилей и контактов отдельно не выгружаются.
В публичных отчётах находятся только сводные числа.

Сравнение шести настроек на одинаковой выборке и доступ к локальному интерфейсу индекса описаны в
[отчёте OpenSearch](search-benchmark.md). Исходные диалоги в отчёт не включены.

`python -m tools.audit_history` отделяет наблюдаемые пустые ответы от возможных исправлений запроса в том же диалоге.
Исправление с тем же номером дома в пределах 30 минут — гипотеза, а не доказательство намерения пользователя.
Прежний ответ бота тоже не является безусловной разметкой: v1 мог выбрать другой город или поменять местами номер улицы и номер дома.
`python -m tools.evaluate_failures` повторяет все запросы с наблюдаемым пустым ответом и отдельно считает найденные коды и варианты с кодами.
Потенциально восстановленный ответ не приравнивается к подтверждённому исправлению.

`python -m tools.evaluate_search --limit 4000` сравнивает v2 с точной копией алгоритма v1 на воспроизводимой выборке.
Корпус разделён по диалогам, а не по случайным сообщениям. Обе части уже просматривались при исправлении регрессий:
это набор повторных проверок, а не независимый набор для окончательной оценки.
Автоматические совпадения, полезные варианты выбора и отказы считаются отдельно.
Одного роста числа находок недостаточно: перед выпуском нужно проверить подмены города, дома, номера улицы и потерю известных ответов.
Проверки настоящих HTTP-запросов, VK SDK, транзакций PostgreSQL и программно созданных событий очереди отделены от имитаций и браузерных кликов.

## Ресурсы и развёртывание

`compose.search.yml` задаёт отдельное локальное окружение. OpenSearch доступен только через localhost,
ограничен 3 ГиБ памяти контейнера и 1 ГиБ кучи JVM.
У немецких контейнеров API, бота и очереди заданы отдельные лимиты памяти, подкачки, процессов и журналов.
Redis остановлен и больше не используется рабочим процессом этой ветки.
Временный обратный туннель к ПК и промежуточный сервис отключены. Немецкий API подключает компактный каталог только для чтения.
Настройки VPN и парольного SSH-доступа не меняются.

При развёртывании должны помещаться рабочие данные и резерв для отката; память нужна также PostgreSQL, боту и VPN.
Полный XML и промежуточная база размером больше 15 ГиБ на небольшой VDS не переносятся.

Предложения ближайших домов пока не реализованы: для них нужны достоверные координаты.
Похожий номер дома или совпадение названия улицы не доказывают географическую близость.
Модель сохраняет идентификатор дома, чтобы позже добавить координаты и новые источники кодов, сохранив происхождение прежних записей.

## Состояние данных на 06.11.2026

Аудит охватывает 2 282 доступных API личных диалога и 198 060 выгруженных сообщений,
в том числе 19 310 пустых ответов, сопоставленных с запросами. Это доступная выгруженная история,
а не атомарный снимок всех сообщений, появившихся во время выгрузки или после неё.

Каталог содержит 34 851 597 действующих домов ГАР, пригодных для поиска.
Из 1 008 682 исходных строк кодов 792 465 однозначно связаны с ГАР; для 9 100 есть неоднозначность,
а 207 117 не удалось привязать. Неподтверждённые адреса сохранены без подстановки дома из другого города.
Получены 108 533 записи домов с кодами и 1 002 183 уникальные строки кодов; 6 499 точных дублей объединены.
Сводки: [каталог](catalog-summary.json) и [аудит истории](history-audit-summary.json).

Реализация прежнего поиска не менялась. Если в исходной строке в поле города записана улица,
v2 не превращает такую строку в автоматический ответ. До проверки записи доступен fallback на v1.

## Исходная проверка до изменения меню выбора

Проверены все 46 611 уникальных элементов корпуса. Среди 43 969 примеров прежних ответов,
которые текущий v1 ещё находит, 30 262 сохраняют этот адрес в автоматическом ответе,
включая 1 508 переходов к v1; ещё в 13 705 случаях адрес присутствует среди вариантов выбора.
В двух случаях есть расхождение: частичное совпадение названия города и перестановка номера улицы с номером дома.
Намерение пользователя требует проверки: буквальное прочтение v2 само по себе не доказывает правильность ответа.
Автоматических ответов с другим адресом в этом подмножестве не было.
Эти числа описывают сохранность адресов, а не стопроцентную точность или одинаковое удобство интерфейса.

Из 19 310 прежних пустых ответов v2 даёт результат с кодами для 2 676 запросов и варианты с кодами ещё для 1 656.
Среди этих 4 332 потенциально восстановленных запросов 3 587 не находит текущий алгоритм v1.
Ещё 5 382 запроса распознают известный дом без кодов. В этой проверке одинаковые запросы не исключаются.
Найденные кандидаты и признаки текста не доказывают ни намерение пользователя, ни причину старого отказа.

Через настоящий OpenSearch проверены 4 000 элементов корпуса.
Объединённый поиск сохраняет эталонный результат или вариант для 3 897 элементов против 3 895 у одного каталога;
часть автоматических ответов превращается в выбор адреса. OpenSearch поддержан, но на немецкий VDS с 1 ГиБ памяти не установлен.
На ПК при одновременных пакетных проверках каталог показал p50 11,814 мс / p95 189,152 мс;
выборка с OpenSearch — p50 35,580 мс / p95 296,386 мс.
Это не гарантия задержки на VDS и не время полного ответа через VK.

В Linux с настоящим PostgreSQL прошли 137 тестов; одна проверка старого цикла событий намеренно пропущена,
поскольку его замену проверяют тесты постоянной очереди.
[Сводный отчёт](search-validation-summary.json) содержит численные результаты.
Исходные запросы, диалоги и отдельные спорные примеры остаются закрытыми.

## Проверка немецкого тестового окружения

### Повторная проверка после изменения меню и защиты кнопок

Повторены все 46 611 элементов корпуса с новой логикой: среди 43 969 прежних успешных примеров
38 491 сохраняют адрес автоматически (включая 2 471 fallback на v1), ещё 5 475 — среди вариантов с кодами.
Итого сохранены 43 966 адресов. Автоматической подмены другим адресом в этом подмножестве нет.
Три оставшихся случая — неоднозначное название города, перестановка номера улицы и дома,
а также запрос из двух цифр, который v1 трактует как квартал и дом. Нужна проверка смысла, а не подгонка к старому ответу.
Время одного поиска по компактному каталогу на ПК: p50 9,497 мс, p95 127,007 мс без кэша API и доставки VK.
Это проверка предварительной разметки, а не гарантия качества на будущих запросах.

Через обработчики очереди и настоящий VK SDK на Германии проверены: прямой ответ «Мичурина 1а»,
отказ от выбора с удалением кнопок, запрос порядковой улицы без дома и 11 подъездов «Плесецкая 10» в двух сообщениях.
Серия из 40 чередующихся действий не создала больше одного активного задания; код последней группы подъездов отредактирован.
Входящие события для этих проверок созданы программно, получатель — владелец тестового бота. Это не браузерные клики.

### Исходные сетевые замеры

На исходном этапе проверки код коммита `d2a7060`, версия `2.0.0.dev1`, работал со своим компактным каталогом при выключенном туннеле к ПК.
Настоящие HTTP-запросы к адресам с кодами заняли 0,115 с и 0,074 с, к известному дому без кодов — 0,021 с.
Настоящий геозапрос DaData вернул HTTP 200 с вариантами адреса за 0,484 с.
Запрос к v1 занял 22,073 с: прежний алгоритм просматривает исходные строки кодов и вызывает Python-функцию SQLite.
Это несколько функциональных проверок, а не нагрузочный тест или гарантия задержки.

Через настоящие обработчики PostgreSQL и VK SDK прошли программно созданные входящие события:
отправка, выбор адреса, нажатие подъезда с редактированием, геометка и следующий текстовый запрос.
Получателем был аккаунт владельца в тестовом сообществе. Это не проверка реальных браузерных кликов.
Локальные проверки с настоящими клиентами также подтвердили переход к каталогу при отказе OpenSearch
