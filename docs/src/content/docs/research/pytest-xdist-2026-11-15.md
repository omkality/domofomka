## Решение

Для полного набора в CI выбран `pytest -n 4`: это самый быстрый проверенный режим,
который сокращает среднее время pytest на 46,1% относительно последовательного
запуска. Дополнительная нагрузка приходится на стандартный runner GitHub, а не на VDS;
ограничений по памяти или проблем изоляции в замерах не обнаружено.
Локально число процессов выбирается через `-n`; обычный `pytest` без `-n` остаётся
последовательным. Зависимости pytest-xdist и execnet
находятся только в группе `dev` и отсутствуют в рабочих образах API и бота.

## Методика

Исходники и lock-файл зафиксированы в ревизии `b9ffb07`. Использовались одинаковые
882 теста, Python 3.12, pytest 9.0.2 и pytest-xdist 3.8.0. Состав тестов и исходы
сопоставлены по идентификаторам в JUnit XML, а не только по количеству успешных тестов.

В [отдельном запуске GitHub Actions](https://github.com/omkality/domofomka/actions/runs/43728310552)
на одном `ubuntu-24.04` runner выполнены восемь прогонов в порядке
`0 → 1 → 2 → 4 → 4 → 2 → 1 → 0`. Значение `0` означает один процесс pytest без
worker; `1` — один worker xdist. Обратный порядок уменьшает влияние прогрева.
Два повтора показывают воспроизводимость этого замера, но не заменяют длительного
наблюдения за разными runner GitHub.

Образы API и бота собраны из рабочих Dockerfile один раз перед всеми прогонами
и переданы через `TEST_API_IMAGE` и `TEST_VKBOT_IMAGE`. Сборка не входит в сравнение.
Образ PostgreSQL, команда и лимиты берутся из рабочего Compose. Используется
стандартное распределение xdist `load`; фикстуры и приложения ради ускорения не менялись.
Точное временное задание сохранено в
[ревизии эксперимента](https://github.com/omkality/domofomka/blob/b9ffb07/.github/workflows/pytest-xdist-benchmark.yml).
После сравнения workflow удалён, чтобы не запускать восемь наборов при обычной разработке.

## Время на GitHub Actions

В таблице приведено время самого pytest; установка зависимостей, линтеры,
сборка образов, публикация и деплой в него не входят.

| Режим | Первый прогон, с | Обратный прогон, с | Среднее, с |
| --- | ---: | ---: | ---: |
| Последовательно, `-n 0` | 81,48 | 71,05 | 76,27 |
| Один worker, `-n 1` | 74,10 | 72,53 | 73,32 |
| Два worker, `-n 2` | 49,08 | 48,73 | 48,91 |
| Четыре worker, `-n 4` | 41,19 | 40,95 | 41,07 |

Два worker сократили среднее время на 35,9%. Даже относительно более быстрого
последовательного прогона выигрыш составляет 31,2%. Четыре worker экономят ещё
7,84 секунды, или 16,0% относительно двух. Ускорение всего CI будет меньше:
остальные этапы не распараллеливаются этой настройкой.

Самая долгая одиночная проверка ждёт сетевой таймаут около 20 секунд.
Параллельный запуск позволяет выполнять другие тесты в это время, но не сокращает
сам проверяемый таймаут.

## Ресурсы

CPU-время измерено `/usr/bin/time` как сумма user и system для запуска тестов
и дочерних процессов; CPU Docker-контейнеров в эту величину не входит.
Память контейнеров опрашивалась через Docker API примерно раз в секунду
плюс задержки API. Это наблюдаемый пик суммы working set, без файлового кэша
`inactive_file`, а не строгий максимум и не вся память Docker или компьютера.

| Режим | Среднее CPU-время тестов, CPU-с | Наблюдаемый пик памяти контейнеров, МиБ | PostgreSQL одновременно |
| --- | ---: | ---: | ---: |
| `-n 0` | 19,57 | 170,1 | 1 |
| `-n 1` | 20,01 | 166,3 | 1 |
| `-n 2` | 24,39 | 199,6 | 2 |
| `-n 4` | 34,54 | 227,5 | 4 |

Четыре worker увеличивают CPU-время тестов на 41,6% относительно двух.
Давления на память runner не наблюдалось: во всех выборках оставалось не менее
13,8 ГиБ `MemAvailable`. Поэтому для CI выбраны четыре worker: дополнительное
CPU-время и память укладываются в доступные ресурсы runner, а время ожидания
меньше. Локально можно выбрать два процесса, если важнее уменьшить расход ресурсов.

На Windows с Docker Desktop первый набор показал ту же тенденцию:

| Режим | Время pytest, с | Пик RSS процессов Python, МиБ | Наблюдаемый пик памяти контейнеров, МиБ |
| --- | ---: | ---: | ---: |
| `-n 0` | 171,32 | 122,5 | 211,9 |
| `-n 1` | 168,02 | 219,0 | 175,4 |
| `-n 2` | 114,01 | 315,2 | 229,5 |
| `-n 4` | 108,09 | 518,8 | 239,4 |

Это ориентировочный локальный замер, не основание для сравнения скорости ОС.
Повторный Windows-прогон `-n 4` также прошёл, но исключён из сравнения времени:
одновременно другой проект пересоздавал свои контейнеры и запускал проверки.
Окончательное решение основано на двух повторах каждого режима на отдельном runner.

## Изоляция и очистка

Во всех восьми Linux-прогонах прошли те же 882 теста. На Windows во всех выполненных
прогонах прошёл 881 тест и ожидаемо пропущена одна Linux-проверка файловой блокировки.
Сопоставление JUnit не обнаружило потерянных, дублирующихся или изменивших исход тестов.

`scope="session"` означает одну фикстуру на каждый worker, поэтому каждый процесс
получает собственный PostgreSQL и Docker-сеть. Внутри worker очереди изолированы
идентификатором сообщества, проверки DDL и каталога — отдельными временными БД.
Реальные транзакции и конкурирующие соединения сохранены. Приложения проверяются
в тех же образах и с теми же ограничениями Compose; монтирования исходников нет.

После каждого Linux-прогона проверено отсутствие оставшихся тестовых контейнеров.
После локального сравнения также не осталось тестовых сетей. Ни перезапуск VDS,
ни тестовая нагрузка на dev/prod для этого сравнения не требуются: Docker и pytest
работают на ПК и GitHub-hosted runner. Полный набор при этом остаётся проверкой
перед обычным деплоем dev через CI/CD.
