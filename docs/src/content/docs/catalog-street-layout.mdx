## Получение кандидатов

Полный GIN по `to_tsvector('simple', words)` используется для улиц; отдельный частичный
GIN `WHERE has_codes=1` обслуживает первый поиск по адресам с кодами. Для вариантов
названия есть GIN в `alias_search`. Выбранные дома, подъезды и коды читаются по B-tree/PK.

<C4View viewId="catalogReadPlan" />

GIN выдаёт подходящие строки, после чего SQL читает названия и задаёт устойчивый порядок
кандидатов. Каталог загружается с группировкой одинаковых `street_key`: близкие строки
занимают меньше разнесённых страниц. Физический порядок не заменяет `ORDER BY` и не
меняет результат ранжирования.

## Номера домов

Дома с кодами находятся в связанных таблицах. Все остальные известные дома ГАР не
разворачиваются в десятки миллионов SQL-строк: `street_houses.data` содержит сжатый набор
номеров и адресных сведений улицы. Читатель распаковывает только ограниченный набор кандидатов.
Словарь `vocabulary` загружается лениво один раз на процесс.

## Обслуживание

Обычный запуск не перестраивает индексы. Каталог собирается отдельно и публикуется
проверенной ревизией. Для уже загруженного dev доступна разовая операция упорядочивания
через Actions `optimize_catalog`: временный индекс, `CLUSTER`, удаление временного индекса
и `ANALYZE` выполняются в транзакции после проверки места. Запуск не входит в обычный деплой.

В рабочем пути нет materialized view: подготовленные поисковые таблицы уже содержат
нужную модель чтения. Схема и миграции описаны в [БД](database.mdx).
