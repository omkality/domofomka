## Границы компонентов

`src/code_service/main.py` собирает HTTP-приложение. `api/routes/v1` и `api/routes/v2`
содержат только обработчики запросов; `services/v1` и `services/v2` — сценарии поиска
и их зависимости. Бот обращается к сервису по HTTP. Общие сетевые настройки,
измерения и миграции находятся в `src/infrastructure`.

`tools` содержит отдельно команды подготовки каталога, истории, оценки,
экспериментов, конфигурации и операций. Приложения их не импортируют.
`ops` содержит ограниченные программы хоста. Конфиги штатных средств ОС находятся
в `ops/config`, units — в `ops/systemd`; Python устанавливает готовые файлы.

## Стиль исходников

Black и Ruff используют строку до 120 символов. Ruff проверяет короткие docstring
модулей, классов, функций и методов приложений и инструментов. Описательные имена
тестовых функций не требуют дублирующей строки документации.

Mypy проверяет аннотации функций приложений, `ops`, `tools` и общих фикстур; отсутствие аннотации
параметра или результата — ошибка `no-untyped-def`. Для инструментов и общих фикстур
соответствующие проверки Ruff также включены. `Any` остаётся допустимым для фактически
динамических внешних границ, а не заменяет известные типы параметров и результатов.

DDL находится в версионируемых SQL-файлах yoyo. Прикладные параметризованные
запросы остаются рядом с кодом читателя или репозитория. SQL оформляется пробелами
по [стилю Mozilla](https://docs.telemetry.mozilla.org/concepts/sql_style): отступ два
символа, ключевые слова в верхнем регистре, имена и функции в нижнем, основные
предложения с одной границы на отдельных строках, явные `AS` и тип `JOIN`.
`AND`/`OR` начинают строку, запятые завершают элементы. Значения передаются параметрами драйвера;
имена динамических объектов — через безопасные идентификаторы Psycopg.
SQLFluff проверяет структуру и оформление SQL-ресурсов; диалект SQLite задан явно.

Новые миграции добавляются отдельной ревизией с зависимостью и SQL отката.
Уже применённые файлы не редактируются. [Порядок работы с миграциями](database.mdx#sql-миграции).
Их прежнее оформление сохраняется: изменение пробелов тоже изменило бы контрольную
сумму yoyo. Коррелированные подзапросы и блокировки очереди не переписываются в CTE
ради оформления: здесь важнее сохранить транзакционное поведение.

## Драйверы и цикл событий

SQLite читает стандартный `sqlite3`; дополнительного асинхронного драйвера нет.
HTTP-сервис запускает чтение v1 через `asyncio.to_thread`, открывая и закрывая
подключение внутри потока. Исходная база открывается только для чтения (`mode=ro`);
порядок кодов и правила v1 сохранены.

Рабочий v2 всегда создаёт `PostgresCatalog` по `CATALOG_DATABASE_URL`.
Переменных `SEARCH_BACKEND` и `SEARCH_CATALOG_PATH` у приложения нет.
SQLite-эталон v2 находится в `tools/catalog/sqlite_catalog.py`: он используется
при подготовке данных и в сравнительных тестах. Его адаптер `AsyncReferenceReader`
воспроизводит сценарий API в офлайн-инструментах, не добавляя SQLite-режим рабочему сервису.

Для PostgreSQL используется Psycopg 3, для HTTP — HTTPX. Читатель v2 выполняет SQL
через `AsyncConnection`: ожидание БД не занимает поток и не блокирует цикл событий.
На процесс сохраняется одно read-only соединение с `autocommit`; `asyncio.Lock`
ограничивает число одновременно выполняемых поисков. Общий дедлайн включает ожидание
блокировки, подключение, SQL и вычисления. После ошибки, таймаута или отмены активной
операции соединение закрывается; следующий запрос создаёт новое. Отмена ожидающего
запроса не закрывает соединение другого запроса. Разбор, распаковка и ранжирование
выполняются через `asyncio.to_thread`, используя общие правила из `ranking.py`.

Бот асинхронно удерживает advisory lock сообщества и проверяет это соединение heartbeat-запросом.
Приём, обработка, восстановление истории, диагностика и обслуживание inbox/outbox
используют `AsyncConnection`. Блокировка строк, запись эффектов и фиксация задания
сохраняют прежние границы транзакций. `QUEUE_DB_MAX_CONCURRENT` ограничивает число
одновременных транзакционных соединений бота (по умолчанию четыре); сессия guard
отдельная и не занимает этот бюджет. Ожидание свободного места ограничено
`QUEUE_DB_CONNECT_TIMEOUT_SECONDS`, SQL — существующим `QUEUE_DB_STATEMENT_TIMEOUT_MS`.
Соединение закрывается после операции; постоянный пул и дополнительная библиотека не нужны.

Каждый worker переиспользует один `httpx.AsyncClient` для внутреннего API и закрывает
его при остановке. Потоки остаются для блокирующего VK SDK и его Long Poll.
Отмена отправки ждёт завершения начатого вызова SDK, в том числе при повторной отмене,
до освобождения runtime. Транзакция БД во время ожидания VK не удерживается.
Если подтверждение не записалось, повтор использует сохранённый `random_id` из outbox.
Команды `vkbot.manage` вызывают тот же асинхронный `QueueStore` через CLI runner;
отдельной синхронной копии очереди нет.
Yoyo и последовательные инструменты подготовки используют синхронный Psycopg.
Это два режима одного драйвера; второй PostgreSQL-клиент не устанавливается.

На Windows асинхронному Psycopg нужен `SelectorEventLoop`. CLI проекта запускаются
через `src.infrastructure.event_loop.run_async`, тесты используют соответствующую
фикстуру. HTTP API с PostgreSQL локально запускают в Docker/Linux: Granian на Windows
выбирает несовместимый Proactor. Серверные контейнеры работают под Linux.

Бот использует HTTPX
с общим дедлайном поверх фазовых таймаутов; синхронный VK SDK сохраняет свой
requests-адаптер. В текущие рабочие зависимости не входят `aiosqlite`, `asyncpg`,
`aiohttp` и отдельный клиент DaData.
Приёмник выпуска на хосте и автономная приёмка используют стандартный
`urllib.request`: это позволяет запускать их без установки зависимостей приложения.
Новая сторонняя HTTP-библиотека ради этих служебных проверок не добавляется.

## Тесты

| Каталог | Что проверяет |
| --- | --- |
| `tests/unit/search` | Разбор адресов, номера домов, ранжирование и ограничения идентичности. |
| `tests/unit/bot` | Представление ответов, клавиатуры и сценарии процессора с заменёнными внешними границами. |
| `tests/unit/infrastructure` | Настройки, HTTP-повторы, маршрутизацию, кеш и измерения. |
| `tests/integration/api` | Настоящую маршрутизацию Litestar и HTTP-контракт версий. |
| `tests/integration/database` | Реальный PostgreSQL: очередь, лимиты, атомарность, миграции и диагностику. |
| `tests/integration/catalog` | Построение и публикацию каталогов, происхождение кодов. |
| `tests/integration/operations` | Контракты Compose, развёртывание, хранение и конфиги хоста. |

Общие фикстуры подключает `tests/conftest.py` из `tests/fixtures`.
SQL-тесты запускают PostgreSQL через Testcontainers и используют изолированные
сообщества или временные БД. Живая ограниченная приёмка вынесена в
`tools.operations.dev_acceptance`; она не рассылает сообщения пользователям.

```bash
uv sync --frozen --all-groups
uv run --frozen --all-groups pre-commit install
uv run --frozen --all-groups pre-commit run --all-files
uv run --frozen --all-groups python -m pytest
```

`.env.example` задаёт общий порядок и состав полей; `.env.dev.example` отличается
значениями профиля. `tools.configuration.environment --check-examples` проверяет
их полноту относительно моделей настроек. Нормализация настоящего файла выполняется
явно с `--file <файл> --profile dev --write`; перед записью сохраняется закрытая копия.
Уже заданные значения, подстановки и дополнительные поля сохраняются.

Проверки CI запускаются до публикации образов. [Развёртывание и откат](cicd.mdx).

### Как проверяется инфраструктура

Testcontainers сам запускает одноразовый PostgreSQL и удаляет контейнер вместе
с анонимным томом после сессии. Образ с digest, команда и ограничения памяти
берутся из `docker-compose.yml`, а не дублируются в фикстуре или GitHub Actions.
Compose разрешается с `.env.example`: личные `.env` и рабочие пароли не читаются.
Порт выбирается автоматически и публикуется только на loopback; готовность
проверяется по TCP, после окончания инициализации PostgreSQL.

Контейнер PostgreSQL и отдельная Docker-сеть имеют `scope="session"`, чтобы не
тратить время на одинаковую инициализацию. Yoyo-миграции общей очереди применяются
один раз. Очереди разных тестов изолируются по сообществам и очищаются после теста.
Проверки DDL и каталога получают отдельные БД с `scope="function"`; временная БД
удаляется целиком после проверки. Транзакции действительно фиксируются: общий
rollback вокруг теста не подменяет работу независимых соединений worker.

Для запуска достаточно работающего Docker:

```powershell
uv sync --frozen --all-groups
uv run --frozen --all-groups python -X utf8 -m pytest
```

Внешний DSN SQL-тестам не передаётся; `TEST_QUEUE_DATABASE_URL` больше не используется.
Недоступный Docker означает ошибку интеграционной фикстуры, а не успешный прогон
с пропущенными SQL-проверками. Unit-тесты (`pytest tests/unit`) не запускают контейнеры.
Testcontainers установлен только в группе `dev`; его Ryuk закреплён по версии и digest.

С настоящей БД проверяются SQL, миграции и откат, блокировки, конкуренция worker,
отмена транзакций, аренда заданий, дедупликация, лимиты и диагностические SAVEPOINT.
HTTP-контракт проверяется через Litestar TestClient; отдельные сетевые ошибки — через
HTTPX MockTransport и моки VK SDK. Дополнительно Testcontainers запускает настоящий
Linux-образ API и проверяет HTTP-поиск и чтение выбранного дома в PostgreSQL без
файлового каталога v2; образ бота выполняет команду диагностики очереди. VK и DaData
в этих тестах не вызываются. Настройки безопасности и ресурсы приложений берутся
из рабочего Compose; исходники с хоста в контейнеры не подмешиваются.

Локально рабочие Dockerfile собираются один раз за сессию, временные теги удаляются
после проверок. В CI образы сначала собираются штатным шагом, затем передаются
фикстуре через `TEST_API_IMAGE` и `TEST_VKBOT_IMAGE`. Именно эти проверенные образы
публикуются для деплоя; повторной сборки после тестов нет. Проверки сценариев
деплоя отдельно подменяют команды Docker/SSH. Живая приёмка выпуска на dev выполняется отдельно.
