Проверка начата **14 ноября 2026 года** на dev от `c848314` (2.0.1).
Master и prod не изменяются. Этот документ отделяет обнаруженные недостатки,
внесённые изменения и варианты, которые не дают достаточного выигрыша.

## Что используется на самом деле

Поиск v2 — лексический: PostgreSQL `to_tsvector('simple', words)` с полным и частичным
GIN, B-tree для точных ключей, словарь и ранжирование RapidFuzz в Python.
`pgvector`, эмбеддингов, векторных индексов и RAG нет. OpenSearch — отключённый
адаптер сравнения; Dashboards не является зависимостью рабочего приложения.

ГАР импортируется и проверяется локально. На VDS находятся опубликованный каталог
PostgreSQL, исходная SQLite v1 и её индекс. Сжатые наборы домов без кодов хранятся
в `street_houses`, а не загружаются целиком в память приложения.

## Внесённые изменения

| Наблюдение | Решение | Почему это оправдано |
| --- | --- | --- |
| Рабочие образы содержат `uv` и `uvx`, хотя зависимости уже установлены | Установка в отдельной стадии, перенос только `.venv`, запуск готовых бинарных файлов | Меньше образ и поверхность поставки; сервер не устанавливает зависимости при старте |
| Оба приложения получают весь `src` | В каждом образе только его компонент и общая инфраструктура | Границы сборки совпадают с проверяемыми границами импортов |
| Healthcheck запускает Python с многострочной программой | Один статический `wget` из официального BusyBox, версия и digest зафиксированы | Проверяется реальный HTTP-статус без дополнительного интерпретатора; полный curl с пакетным менеджером не устанавливается |
| Dev Compose дублирует почти все сервисы основного файла | `extends` и явные dev-переопределения через `!override` | Единые лимиты и настройки; dev не наследует содержимое prod `.env` |
| Настройки PostgreSQL записаны парами `-c` / значение | Эквивалентные `--параметр=значение` | Понятнее список аргументов; все настройки остаются в `.env`, без собственного конфигуратора PostgreSQL |
| В корне лежит Compose сравнения с необязательным Dashboards | Окружение сравнения отделено от рабочих Compose; неиспользуемый Dashboards удалён | Исключается случайный запуск тяжёлой панели на VDS; методика сравнения остаётся воспроизводимой |
| `Processor` содержит оформление сообщений и сетевой RateGate | Чистые функции в `presentation.py`, транспорт и ограничитель в `http.py` | Планировщик отвечает за сценарий; представление тестируется без сети и очереди |
| В исходном v1-сканировании SQL собирается f-строкой | Параметризованный запрос; `logger.exception` вместо форматирования traceback | Однообразная работа с SQL и журналом; алгоритм совпадения и порядок результата сохраняются |
| Ruff содержит удалённые правила и настройки неиспользуемого FastAPI | Удалены неработающие настройки | Проверка больше не предупреждает о правилах, не влияющих на код |
| Документация — плоский набор текущих и исторических Markdown | Русская статическая вики, LikeC4 с walkthrough, отдельный раздел исследований | Текущее устройство не смешивается с результатами старых экспериментов |

Значения настройки PostgreSQL через `-c` были корректны: сервер также официально
поддерживает `--name=value`. Это улучшение читаемости, а не исправление ошибки БД.
[Документация PostgreSQL](https://www.postgresql.org/docs/17/config-setting.html).

## Что оставлено прежним

### Границы компонентов и версий

`vkbot`, `code_service` и `infrastructure` уже разделены. Внутри сервиса кодов
`v1` и `v2` имеют свои HTTP-роуты, сценарии и доступ к данным. Между версиями
есть явный проверяемый fallback; обратная зависимость v1 от v2 запрещена тестами.
Новые общие интерфейсы, контейнер внедрения зависимостей и пустые пакеты под v3
не добавляются. Для небольшого проекта это усложнило бы навигацию без пользы.

Большие транзакционные методы очереди не разрезаются на абстрактные репозитории:
сохранение курсора, дедупликация, лимиты пользователя и план outbox должны оставаться
в согласованных транзакциях. Вынос SQL ради длины файла не улучшает эту гарантию.

### Requests и HTTPX

`vk-api` использует интерфейс `requests.Session`; на него завязаны реальные попытки,
общий RateGate, SDK Long Poll и обработка ответа VK. HTTPX используется асинхронным
геокодером и внутренним HTTP-вызовом с общим дедлайном, включающим чтение тела.
Эти случаи покрыты тестами с медленным телом и отменой запроса. Простая замена
на Requests изменила бы семантику общего таймаута. `aiohttp` и `pyreqwest` в рабочей
сборке отсутствуют. Переписывать SDK или адаптировать его протокол ради одного имени
HTTP-библиотеки здесь дороже, чем сохранить две явно ограниченные области применения.

### Базовые образы

Python slim остаётся поддерживаемым Debian-образом: совместим с бинарными зависимостями
Granian, psycopg и RapidFuzz, не требует компилятора на VDS. Переход на Alpine только ради
нескольких мегабайт без отдельного прогона musl-сборок не обоснован. PostgreSQL уже
использует официальный Alpine-образ. Версии и digest закреплены; рабочий деплой принимает
только digest образов приложения. Подвижные `latest` не используются для выпуска.

Старый Python-healthcheck сохраняется только в замороженном сценарии отката v1:
его образ не содержит `wget`, а зависимости резервного выпуска не изменяются задним числом.

### Надёжность и ресурсы

Inbox/outbox, постоянный `random_id`, аренда задач, сверка истории, ограничения по
пользователю и принятые правила подавления подсказок остаются прежними. Ротация логов,
лимиты памяти/PID, read-only rootfs, non-root, снятые capabilities и аварийный резерв
диска сохраняются. Кеш ограничен и количеством, и байтами. Секреты и данные пользователей
не входят ни в Docker-контекст, ни в сайт документации.

Прокси не получает отдельного фонового мониторинга. Реальные сетевые запросы меняют
процессное состояние маршрута; неизвестные мутации не повторяются автоматически.

## Индексы и материализованные представления

Проверяются реальные существующие индексы, статистика использования и планы запросов
на опубликованном каталоге. Оптимизация не должна дублировать уже подготовленные
`streets`, `alias_search`, `vocabulary` и сжатые наборы домов. Это готовая модель чтения:
дополнительная materialized view потребовала бы места и отдельного порядка обновления.

Новый индекс, удаление старого индекса или materialized view допускаются только после
сравнения `EXPLAIN (ANALYZE, BUFFERS)`, размера и результата поиска на одинаковых данных.
**Решение после измерений: новых индексов и materialized view не добавлять.**

- На изолированной восстановленной копии той же ревизии каталога проверены 43 уникальных
  сочетания SQL и параметров, полученных из восьми реальных сценариев читателя.
  План измерялся через `EXPLAIN (ANALYZE, BUFFERS)`, а не по предполагаемой форме запроса.
  Обычные запросы занимали менее 0,46 мс; используются существующие GIN и точные B-tree.
- Самый медленный локальный SQL — однократное чтение 146 962 слов словаря с сортировкой
  `COLLATE "C"`, около 38,4 мс. Словарь кешируется на процесс: отдельный индекс ради
  этой сортировки при запуске не окупает дополнительное хранение. Это не время всего поиска.
- На Германии роль API в read-only транзакции выполнила контрольный поиск по «мичурина»
  через `coded_street_words`: 30 строк, 26 попаданий в shared buffers, без чтений диска
  и временных записей; execution time 1,315 мс, planning time 9,854 мс.
  Это один прогретый план, не p95 и не оценка холодного диска.
- `pg_stat_user_indexes` подтверждает использование `building_lookup`, `building_street`,
  `alias_house`, `alias_words`, полного и частичного GIN. На dev каталог занимает около
  1,04 ГиБ; расширение PostgreSQL только `plpgsql`, `pgvector` не установлен.
- Очередь dev занимает около 9,8 МиБ: оценочно 222 inbox, 143 outbox и 18 строк состояния.
  Индексы готовых задач, порядка пользователя и незавершённых действий уже используются.
  Seq Scan маленькой таблицы состояния сам по себе не является проблемой. Нулевой счётчик
  очистки контекста не доказывает ненужность индекса: срок очистки мог ещё не наступить.

Счётчики включают фоновые проверки, а не только пользовательские запросы. Локальные
задержки нельзя переносить на VDS. Полный HTTP-поиск включает Python, чтение/распаковку
домов и иногда fallback: быстрый GIN не обещает мгновенный ответ во всех сценариях.
Материализованное представление сейчас дублировало бы подготовленный каталог и добавило
refresh/согласование ревизий; ускоряемого повторяющегося агрегата в рабочем пути не найдено.

## Документация и малые VDS

Astro/Starlight собирается на ПК или GitHub Actions. LikeC4 рассчитывает модель при
сборке, а интерактив выполняется в браузере. На серверах бота нет Node, npm, Graphviz,
Dashboards или отдельного приложения документации. Готовая статика ограничена бюджетом
32 МиБ; реальный размер фиксирует `npm run build`. Пошаговые dynamic views используют
официальный [LikeC4 Vite Plugin](https://likec4.dev/tooling/vite-plugin/).

## Граница будущей v3

OpenSearch, семантический поиск и распознавание голосовых/кружков сейчас не реализуются.
При появлении данных и оценки качества v3 сможет получить собственный пакет HTTP API;
распознавание вложения должно выдавать текст, который проходит тот же сценарий поиска.
Формат результата и планирование доставки остаются отдельными от поискового движка.
Платформы плагинов, брокеры, векторные расширения и новые сервисы заранее не поднимаются.

## Проверки

Исходная версия: **838 тестов прошли, 1 пропущен** локально с отдельным PostgreSQL.
После изменений: **840 прошли, 1 пропущен** (84,62 с). Добавлены проверки настоящего
Compose merge: секреты prod не попадают в dev, лимиты и параметры БД наследуются.

| Проверка | Подтверждённый локальный результат |
| --- | --- |
| Образы в одном Docker engine, прежний и новый Dockerfile | API: 86 420 802 → 68 273 047 байт (−21%); бот: 71 513 413 → 52 583 193 (−26,5%) |
| Runtime | Импорты, UID/GID 10001, read-only rootfs, capabilities=0, no-new-privileges; uv/uvx и чужой компонент отсутствуют |
| Совместимость отката | Абсолютный путь Python запускается в прежних API/bot образах; для отката используется сохранённый Compose соответствующего выпуска |
| HTTP-healthcheck | HTTP 200 принят; HTTP 503 отклонён даже при PYTHONOPTIMIZE=1; медленный ответ прерван примерно за 1,18 с при лимите 1 с |
| Настоящий API нового образа | Поиск v1/v2 на восстановленном PostgreSQL и исходной SQLite: точный адрес, подъезд в запросе, несколько адресов, порядковая улица, дом без кодов |
| Зависимости | pip-audit: 39 пакетов рабочего окружения, известных уязвимостей не найдено; npm audit после обновления Astro: 0 |
| Документация | LikeC4 валиден; статический сайт около 5,8 МиБ; внутренние ссылки проверяются сборкой; Start/Next/Previous проверены в браузере |

Размеры образов — измерение `docker image inspect` в одном движке; это не сумма уникальных
слоёв на VDS и не расход RAM. Для dev проверены совместимость Compose (5.0.0), действующие
индексы, свободное место и отсутствие OOM/перезапусков до переключения.
Дальнейшую приёмку точной опубликованной ревизии выполняет CI/CD. Успешная проверка dev
не является выпуском prod.
