# Очередь, резервные копии и контроль ресурсов dev

Эта инструкция относится к ветке `dev`. Прод при её разработке не изменялся.

## Каталог v2

На Германии v2 читает отдельную БД того же PostgreSQL через роль только для чтения.
Исходная SQLite и её индекс используются v1; рабочей SQLite-копии v2 на VDS нет.
Схема, связи и порядок публикации: [database.md](database.md).
Фактические лимиты и проверки: [отчёт переноса](postgres-dev-2026-11-06.md).

Каталог неизменяемый и резервируется при публикации. Проверенный дамп находится вне VDS,
в закрытой папке проекта; на VDS оставлен манифест. Ежедневный таймер ниже копирует изменяемую очередь.
Автоматическая доставка новых копий очереди во внешнее хранилище пока не настроена.

При восстановлении нужны проверенный дамп, создание отдельной БД, роль с CONNECT/USAGE/SELECT
и обновление CATALOG_DATABASE_URL/CATALOG_REVISION. Между каталогом и очередью нет внешних ключей.
Нельзя удалять БД очереди, её том или сбрасывать последовательности ID ради обновления каталога.
Текущего свободного места недостаточно для двух полных копий каталога одновременно:
нужны расчёт места, проверенная offsite-копия и запланированное переключение.
После приёмки миграции временный SQLite-снимок для отката удалён;
SEARCH_BACKEND=sqlite заработает только после восстановления соответствующего файла.

## Очистка без повторной рассылки

Раз в `QUEUE_MAINTENANCE_INTERVAL_SECONDS` (по умолчанию 300 секунд) бот обрабатывает не более
`QUEUE_MAINTENANCE_BATCH` завершённых заданий. По умолчанию тела входящих и исходящих заданий хранятся 30 дней,
контекст кнопок — 60 дней. Срок считается по завершению, а не получению сообщения.

Входящее задание удаляется только после успешной доставки всех его исходящих действий и окончания срока хранения.
`pending`, `processing`, `deferred`, `failed` не удаляются. Очистка контекста пропускает диалоги с незавершёнными заданиями и ошибками.
Старый выбор адреса после истечения контекста получает просьбу прислать адрес снова, без восстановления старого меню.

Перед удалением сохраняется `(group_id, event_key)` в `bot_receipts` без текста запроса и ответа.
Запись и удаление выполняются одной транзакцией; сбор событий и сверка истории используют ту же блокировку.
Повторно полученный старый запрос не создаёт новую отправку. Последовательности ID не сбрасываются:
новые исходящие задания сохраняют уникальность `random_id`.

Журнал идентификаторов остаётся бессрочным и постепенно растёт. Поэтому очистка уменьшает объём содержимого,
но не обещает постоянный размер всей БД. Autovacuum позволяет повторно использовать освобождённые страницы;
размер файла БД после удаления не обязан сразу уменьшиться. `VACUUM FULL` в рабочем процессе не запускается.

## Состояние и предупреждения

```bash
docker compose -p domofomka-dev --env-file .env.dev -f docker-compose.yml exec -T vkbot uv run --frozen python -m src.vkbot.manage health
```

Вывод содержит размер БД, количество записей по состояниям, возраст старейших заданий и число сохранённых идентификаторов.
В журнале бота появляется предупреждение при наличии `failed`, долгом ожидании активного задания,
превышении порога размера БД или недостатке свободного места. Пороги задаются в `.env`:

- `QUEUE_DISK_FREE_MIN_BYTES=268435456` — 256 МиБ свободного места;
- `QUEUE_DATABASE_WARN_BYTES=134217728` — размер БД 128 МиБ;
- `QUEUE_OLDEST_PENDING_WARN_SECONDS=120` — возраст ожидающего или выполняющегося задания.

Это предупреждения в журнале, а не отправка уведомлений владельцу. Внешний мониторинг может читать эти данные.
Ограничения Docker и ротация журналов остаются включёнными. Для PostgreSQL отдельно заданы небольшие
`shared_buffers`, `work_mem`, память обслуживания, число соединений и один процесс autovacuum; настройки находятся в примерах `.env`.

WAL и временные файлы ограничиваются QUEUE_MAX_WAL_SIZE, QUEUE_MIN_WAL_SIZE и QUEUE_TEMP_FILE_LIMIT.
Max WAL — целевой размер, а не жёсткая квота; перед восстановлением дополнительно проверяется диск.
Размер БД в `manage health` относится к очереди, а не ко всему экземпляру PostgreSQL с каталогом.

Рабочие образы устанавливают только свою группу зависимостей без dev-пакетов и кеша uv.
UV_NO_SYNC запрещает установку пакетов при запуске; изменение зависимостей требует пересборки образа.
Сборку и импорты минимальных образов проверяет CI. Переменные описаны в
[документации uv](https://docs.astral.sh/uv/reference/environment/#uv_no_sync).

## Резервная копия и проверка восстановления

На хосте dev:

```bash
DOMOFOMKA_ROOT=/root/domofomka-dev bash ops/queue-backup.sh --verify
```

Скрипт создаёт согласованную копию `pg_dump --format=custom` в `backups/queue/` с закрытыми правами.
Сначала проверяет запас места и записывает временный файл. Готовая копия публикуется только после успешного завершения.
Один запуск защищён `flock`; старые копии удаляются после `QUEUE_BACKUP_KEEP_DAYS` (по умолчанию три дня),
при этом сохраняются минимум две последние. `QUEUE_BACKUP_RESERVE_BYTES` по умолчанию оставляет 256 МиБ запаса сверх оценки размера БД.

`--verify` восстанавливает копию в новую БД с префиксом `domofomka_restore_check_`, проверяет чтение таблицы и удаляет проверочную БД.
Действующая БД не подменяется. Простая проверка заголовка архива выполняется и без этого флага.

Для ежедневного запуска предусмотрены `ops/domofomka-dev-backup.service` и `.timer`.
Время — 03:30 UTC с разбросом до 15 минут, то есть 06:30–06:45 по Москве.

```bash
install -m 644 ops/domofomka-dev-backup.service /etc/systemd/system/
install -m 644 ops/domofomka-dev-backup.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now domofomka-dev-backup.timer
systemctl list-timers domofomka-dev-backup.timer
```

Копия на том же VDS не защищает от потери его диска. Проверенную копию нужно хранить и вне сервера.
Переписки входят в дамп: каталог `backups/` исключён из Git и Docker-контекста.
Нельзя запускать восстановленную старую очередь параллельно с действующей: можно повторно отправить уже доставленные ответы.

## Отложенная геолокация

При временной ошибке определения адреса бот один раз сообщает, что запрос сохранён, и предлагает адрес текстом.
Уведомление и отложенная задача сохраняются атомарно. Отложенная задача не блокирует последующие сообщения этого диалога.

По умолчанию повтор начинается через 60 секунд и допускается в течение 30 минут.
Настройки — `GEO_RETRY_DELAY_SECONDS` и `GEO_RETRY_MAX_AGE_SECONDS`.
Следующее входящее сообщение отменяет старую геолокацию. Проверка повторяется перед подготовкой и отправкой ответа.
Уже начатый внешний запрос отменить задним числом нельзя; остаётся небольшое окно между последней проверкой и приёмом запроса VK.

Повторная ошибка не создаёт новое предупреждение. После истечения времени геолокация остаётся как `failed` с причиной
`GeoRetryExpired`, без вечного опроса DaData и без пометки об успешной выдаче кода.
Команда `retry-failed` открывает для неё новое окно попыток. Новый адрес пользователя делает такую задачу устаревшей.
Уже подготовленный ответ продолжает доставляться через outbox после окончания окна геокодирования, если запрос не заменён новым.
# Развёртывание

[Политика хранения, аварийный резерв и копии на ПК](storage-safety.md) применяется отдельно от выпуска приложения.

Новые версии приложения доставляются через [CI/CD](cicd.md). Не запускайте на рабочем VDS `up --build`
из старой папки исходников: это обойдёт проверенные образы. PostgreSQL и ночные резервные копии
сохраняют существующий Compose-проект. Для чтения статуса достаточно `docker ps` или `docker exec`;
старый Compose допустим для `exec`/`ps`, но не для обновления приложений.
