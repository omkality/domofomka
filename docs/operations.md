# Очередь, резервные копии и контроль ресурсов dev

Эта инструкция относится к ветке `dev`. Прод при её разработке не изменялся.

## Каталог v2

На Германии v2 читает отдельную БД того же PostgreSQL через роль только для чтения.
Исходная SQLite и её индекс используются v1; рабочей SQLite-копии v2 на VDS нет.
Схема, связи и порядок публикации: [database.md](database.md).
Фактические лимиты и проверки: [отчёт переноса](postgres-dev-2026-11-06.md).

Рабочий каталог доступен API только для чтения; его публикация описана в [CI/CD](cicd.md).
Исходные данные и прежние артефакты разработки остаются закрытыми. Ежедневный таймер ниже
копирует изменяемую очередь на сервере; регулярные копии на ПК и внешние оповещения отменены владельцем.

При восстановлении нужны проверенный дамп, создание отдельной БД, роль с CONNECT/USAGE/SELECT
и обновление CATALOG_DATABASE_URL/CATALOG_REVISION. Между каталогом и очередью нет внешних ключей.
Нельзя удалять БД очереди, её том или сбрасывать последовательности ID ради обновления каталога.
Текущего свободного места недостаточно для двух полных копий каталога одновременно:
нужны расчёт места и запланированное переключение; ограниченные изменения dev публикуются обратимым патчем.
После приёмки миграции временный SQLite-снимок для отката удалён;
SEARCH_BACKEND=sqlite заработает только после восстановления соответствующего файла.

## Очистка без повторной рассылки

Активный хвост дополнительно ограничен `QUEUE_MAX_PENDING_MESSAGES_PER_PEER=3`:
старые разные ещё не начатые запросы и целые неначатые outbox-планы заменяются новыми.
Идентификаторы и причина отмены остаются в журнале. Это отдельная политика отбора, а не удаление
при очистке. Уже начатая отправка и частично доставленный ответ сохраняются.
`OUTBOX_PEER_MIN_INTERVAL_SECONDS=5` ограничивает частоту исходящих заданий одного пользователя;
состояние паузы хранится в PostgreSQL. [Сценарии](message-delivery.md#ограничение-накопленного-хвоста).

Раз в `QUEUE_MAINTENANCE_INTERVAL_SECONDS` (по умолчанию 300 секунд) бот обрабатывает не более
`QUEUE_MAINTENANCE_BATCH` завершённых заданий. По умолчанию тела входящих и исходящих заданий хранятся 180 дней,
контекст кнопок — 90 дней. Срок считается по завершению, а не получению сообщения.

Входящее задание удаляется только после успешной доставки всех его исходящих действий и окончания срока хранения.
`pending`, `processing`, `deferred`, `failed` не удаляются. Очистка контекста пропускает диалоги с незавершёнными заданиями и ошибками.
Старый выбор адреса после истечения контекста получает просьбу прислать адрес снова, без восстановления старого меню.

Перед удалением сохраняется `(group_id, event_key)` в `bot_receipts` без текста запроса и ответа.
Запись и удаление выполняются одной транзакцией; сбор событий и сверка истории используют ту же блокировку.
Повторно полученный старый запрос не создаёт новую отправку. Последовательности ID не сбрасываются:
новые исходящие задания сохраняют уникальность `random_id`.

Журнал идентификаторов остаётся бессрочным и постепенно растёт. Поэтому очистка уменьшает объём содержимого,
но не обещает постоянный размер всей БД. Autovacuum позволяет повторно использовать освобождённые страницы;
размер файла БД после удаления не обязан сразу уменьшиться. `VACUUM FULL` в рабочем процессе не запускается.

## Состояние и предупреждения

```bash
docker compose -p domofomka-dev --env-file .env.dev -f docker-compose.yml exec -T vkbot uv run --frozen python -m src.vkbot.manage health
```

Вывод содержит размер БД, количество записей по состояниям, возраст старейших заданий и число сохранённых идентификаторов.
В журнале бота появляется предупреждение при наличии `failed`, долгом ожидании активного задания,
превышении порога размера БД или недостатке свободного места. Пороги задаются в `.env`:

- `QUEUE_DISK_FREE_MIN_BYTES=268435456` — 256 МиБ свободного места;
- `QUEUE_DATABASE_WARN_BYTES=134217728` — размер БД 128 МиБ;
- `QUEUE_OLDEST_PENDING_WARN_SECONDS=120` — возраст ожидающего или выполняющегося задания.

Это предупреждения в журнале, а не отправка уведомлений владельцу. Внешний мониторинг может читать эти данные.
Ограничения Docker и ротация журналов остаются включёнными. Для PostgreSQL отдельно заданы небольшие
`shared_buffers`, `work_mem`, память обслуживания, число соединений и один процесс autovacuum; настройки находятся в примерах `.env`.

WAL и временные файлы ограничиваются QUEUE_MAX_WAL_SIZE, QUEUE_MIN_WAL_SIZE и QUEUE_TEMP_FILE_LIMIT.
Max WAL — целевой размер, а не жёсткая квота; перед восстановлением дополнительно проверяется диск.
Размер БД в `manage health` относится к очереди, а не ко всему экземпляру PostgreSQL с каталогом.

Рабочие образы устанавливают только свою группу зависимостей без dev-пакетов и кеша uv.
UV_NO_SYNC запрещает установку пакетов при запуске; изменение зависимостей требует пересборки образа.
Сборку и импорты минимальных образов проверяет CI. Переменные описаны в
[документации uv](https://docs.astral.sh/uv/reference/environment/#uv_no_sync).

## Резервная копия и проверка восстановления

На хосте dev:

```bash
DOMOFOMKA_ROOT=/root/domofomka-dev bash ops/queue-backup.sh --verify
```

Скрипт создаёт согласованную копию `pg_dump --format=custom` в `backups/queue/` с закрытыми правами.
Сначала проверяет запас места и записывает временный файл. Готовая копия публикуется только после успешного завершения.
Один запуск защищён `flock`; старые копии удаляются после `QUEUE_BACKUP_KEEP_DAYS` (по умолчанию три дня),
при этом сохраняются минимум две последние, а `QUEUE_BACKUP_MAX_COPIES=3` ограничивает число поколений. `QUEUE_BACKUP_RESERVE_BYTES` по умолчанию оставляет 256 МиБ запаса сверх оценки размера БД.

`--verify` восстанавливает копию в новую БД с префиксом `domofomka_restore_check_`, проверяет чтение таблицы и удаляет проверочную БД.
Действующая БД не подменяется. Простая проверка заголовка архива выполняется и без этого флага.

Для ежедневного запуска предусмотрены `ops/domofomka-dev-backup.service` и `.timer`.
Время — 03:30 UTC с разбросом до 15 минут, то есть 06:30–06:45 по Москве.

```bash
install -m 644 ops/domofomka-dev-backup.service /etc/systemd/system/
install -m 644 ops/domofomka-dev-backup.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now domofomka-dev-backup.timer
systemctl list-timers domofomka-dev-backup.timer
```

Копия на том же VDS не защищает от потери его диска. Внешнее резервирование не настроено по решению владельца.
Переписки входят в дамп: каталог `backups/` исключён из Git и Docker-контекста.
Нельзя запускать восстановленную старую очередь параллельно с действующей: можно повторно отправить уже доставленные ответы.

## Отложенная геолокация

При временной ошибке определения адреса бот один раз сообщает, что запрос сохранён, и предлагает адрес текстом.
Уведомление и отложенная задача сохраняются атомарно. Отложенная задача не блокирует последующие сообщения этого диалога.

По умолчанию повтор начинается через 60 секунд и допускается в течение 30 минут.
Настройки — `GEO_RETRY_DELAY_SECONDS` и `GEO_RETRY_MAX_AGE_SECONDS`.
Следующее входящее сообщение отменяет старую геолокацию. Проверка повторяется перед подготовкой и отправкой ответа.
Уже начатый внешний запрос отменить задним числом нельзя; остаётся небольшое окно между последней проверкой и приёмом запроса VK.

Повторная ошибка не создаёт новое предупреждение. После истечения времени геолокация остаётся как `failed` с причиной
`GeoRetryExpired`, без вечного опроса DaData и без пометки об успешной выдаче кода.
Команда `retry-failed` открывает для неё новое окно попыток. Новый адрес пользователя делает такую задачу устаревшей.
Уже подготовленный ответ продолжает доставляться через outbox после окончания окна геокодирования, если запрос не заменён новым.

**Отказ доступа DaData — отдельный случай.** Ответ 401/403 может означать ключ, почту или
исчерпанную суточную квоту; 429 относится к частоте запросов. При 401/403 API отвечает 503
с `geocoding_retryable=false`, в том числе с включённой диагностикой. Бот один раз сообщает:
«Определение адреса по геолокации временно недоступно. Отправьте адрес текстом» и завершает
геозадачу без создания отложенного повтора. Уже отложенная задача при таком ответе тоже
завершается уведомлением. Текстовый поиск продолжает работать.

Защита от внешних обращений общая для клиентов одного процесса API:
`DADATA_ACCESS_COOLDOWN_SECONDS=3600` для отказа доступа и прежний
`DADATA_FAILURE_COOLDOWN_SECONDS=30` для обычных временных ошибок. Она хранится в памяти,
сбрасывается после перезапуска и не определяет время обновления квоты провайдера.
У нескольких процессов состояние отдельное. Успешный закешированный георезультат ещё может
использоваться до своего TTL. Ошибка доступа не переключает прокси на прямое соединение.
Квоту проверяют имитацией ответа, не исчерпанием реального лимита.

# Развёртывание

[Политика хранения, аварийный резерв и серверные копии](storage-safety.md) применяется отдельно от выпуска приложения.

Новые версии приложения доставляются через [CI/CD](cicd.md). Не запускайте на рабочем VDS `up --build`
из старой папки исходников: это обойдёт проверенные образы. PostgreSQL и ночные резервные копии
сохраняют существующий Compose-проект. Для чтения статуса достаточно `docker ps` или `docker exec`;
старый Compose допустим для `exec`/`ps`, но не для обновления приложений.


## HTTP-клиенты и бюджеты времени

DaData, внутренний API бота, необязательный OpenSearch и инструменты проверки используют HTTPX.
Клиент закрывается до завершения цикла событий; pyreqwest больше не входит в рабочие зависимости.
Существующий VK SDK использует свой requests-адаптер с прежними ограничениями частоты и повторов.
Новых сетевых сервисов или фоновых обработчиков для замены клиента не добавлено.

Для DaData `DADATA_TIMEOUT_SECONDS` (по умолчанию 8 с) — общий бюджет на прокси, прямой fallback,
получение тела и декодирование JSON. `DADATA_CONNECT_TIMEOUT_SECONDS` (2 с) ограничивает соединение
в каждом выбранном маршруте. При ошибке соединения с прокси или CONNECT допускается прямой запрос;
ошибка HTTP и таймаут чтения не вызывают немедленный повтор по другому маршруту.

Внутренний поиск бота ограничен общим бюджетом `INTERNAL_API_TIMEOUT_SECONDS` (30 с), геопоиск —
`INTERNAL_API_GEO_TIMEOUT_SECONDS` (30 с); соединение — `INTERNAL_API_CONNECT_TIMEOUT_SECONDS` (5 с).
Общий дедлайн дополнительно установлен поверх фазовых таймаутов HTTPX, поэтому медленно поступающее
тело ответа не продлевает обработку бесконечно. Необязательный OpenSearch ограничен своим
`OPENSEARCH_TIMEOUT_SECONDS`.

Внутренние запросы и прямой маршрут DaData игнорируют системные `HTTP_PROXY`/`HTTPS_PROXY`.
Маршрут DaData задаётся явно через `DADATA_PROXY_URL`; пустое значение означает прямые обращения.
Проверяющий TLS-контекст переиспользуется внутри процесса; HTTP-клиенты закрываются после своих операций.
Проверка сертификата и имени сервера остаётся включённой.
Штатные INFO-логи HTTPX/httpcore выключены: приватные адреса из URL не дублируются в журнале контейнера.


### Проверка замены клиента на dev, 06.11.2026

Код замены HTTPX опубликован в `7c34e3d`, первая проверенная сборка dev — `f12e82b`.
В Linux CI прошли 300 тестов, одна проверка старого цикла событий пропущена; локально — 299 и два пропуска.
Отдельный интерпретатор проверяется настоящими локальными сокетами и несколькими циклами событий.
Общий дедлайн дополнительно проверен на теле ответа, зависшем после получения HTTP-заголовков.

На Германии все 62 HTTP-ответа совпали с принятым кандидатом каталога.
Прогон из 120 смешанных обращений к API дал p50 5,916 мс, p95 11,958 мс, максимум 180,289 мс.
Это небольшой ограниченный прогон, а не SLA доставки ответа VK.
Прямые обращения и переход после отказа прокси прошли для DaData и VK; сообщения не отправлялись.
Проверены настоящие вызовы внутреннего API из процессора бота: текст, геометка и выбранный дом.
Индексация и поиск HTTPX также проверены на двух искусственных документах локального OpenSearch;
временный индекс после проверки удалён.

Сравнение двух образов на одном VDS: прежний образ после успешного геокодирования завершился кодом 139,
образ с HTTPX — кодом 0. Точная причина сбоя прежнего нативного клиента не установлена;
успешный HTTP-ответ и штатное завершение процесса оцениваются отдельно.
Длительную проверку повторных внутренних запросов выполняют отдельно в ограниченном контейнере,
чтобы отследить RSS и чистое завершение при той же небольшой памяти.


Дополнительная проверка `500155a`/сборки `3cfadc9`: сертификаты загружаются один раз на процесс.
В Linux CI прошёл 301 тест, одна проверка старого цикла событий пропущена.
Контрольный прогон до переиспользования контекста: 120 запросов за 595 с, RSS 62,55 → 71,91 МиБ.
Повторная серия после изменения: 120 запросов за 11,91 с, RSS 63,72 → 63,74 МиБ без дальнейшего роста
после первых запросов. Обе серии выполнялись отдельным процессом с лимитом 128 МиБ и CPU 20%.
Интервалы различались, поэтому времена этих серий не являются сравнительным бенчмарком скорости.
OOM и перезапусков рабочих контейнеров не было; временные тестовые контейнеры удалены.
Это ограниченная проверка, а не гарантия поведения при любом количестве запросов.

Восстановление серверной копии очереди повторно проверено на Германии в отдельной временной БД.
Проверочная БД удалена, сохранены три поколения; последний дамп занимал около 90 КБ.
Из восстановленной копии бот не запускался, копий на ПК не создавалось.
