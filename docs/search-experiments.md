# Сравнение поисковых стратегий

Задача [#10](https://github.com/omkality/domofomka/issues/10), `priority:P1`.
Выпуск v2 приостановлен. Master и prod не меняются.

## Что исправляется до сравнения

Прежняя нормализация объединяла `2-4` и `24`. Это дефект идентичности данных, а не настройки fuzzy.
`tools/repair_house_identity.py` создаёт отдельную копию полной сборки, восстанавливает номер из буквального
адреса и распределяет коды по исходным строкам `codes.db`. Неподтверждённые разные дома не объединяются.
Остальные подтверждённые привязки и исходная v1 сохраняются.

Итоговая сборка исправила 36 940 ключей домов, пересобрала 4 236 исходных строк и перенесла 102 строки
между идентичностями. Все 1 008 682 исходных идентификатора сохранены; расхождений номера между
источником и назначением после исправления нет. Эти числа сами по себе не оценивают поиск.
Отдельно исправлено удаление буквы «Д» внутри номера и проверены буквенные диапазоны вроде `71к4Г-Д`.

Числовой диапазон остаётся отличным от слитного номера и дроби. Проверяются также буквы, корпуса,
строения, номер улицы и запись порядкового номера словами. Наборы с заранее заданными домами
не получают ожидаемые номера из проверяемого нормализатора.

Обратимый патч сверяется целиком с новой сборкой в PostgreSQL с лимитом 192 МиБ: применение,
откат до прежних таблиц и повторное применение. Клиент миграции ограничен 384 МиБ;
в репетиции максимумы составили 293, 226 и 226 МиБ. Исходная база v1 не изменяется.
Исторический прогон также проверяет запись корпуса с разделителем (`5к-1`) и отдельный
номер квартала после корпуса. Совместимость не разрешает заменить номер или букву дома.

## Варианты поиска

1. Рабочий PostgreSQL/RapidFuzz без OpenSearch.
2. Прежний гибрид: кандидаты OpenSearch и общий Python-ранжировщик.
3. Самостоятельное текстовое ранжирование OpenSearch без порога RapidFuzz.

В третьем варианте остаются проверки точного дома, типа адреса и числового номера улицы.
Наличие кодов не разрешает заменить точный дом на соседний. Сравниваются анализаторы без stemming,
с русским stemming и с поисковыми синонимами; edit distance, префикс, число расширений,
полнота совпадения слов, приоритет точного совпадения и ширина группы для уточнения.

Предыдущая матрица в `search-benchmark.md` проверяла только первый и второй варианты:
общий Python-порог мог отвергать полезные кандидаты OpenSearch. Она не доказывает превосходство
Python-поиска над самостоятельным OpenSearch.

## Корпусы и метрики

- Историческая регрессия: прежние успешные ответы и гипотезы исправлений. Это проверка сохранности,
  а не подтверждённая точность намерения пользователя.
- Ручная разметка: ограничения по улице, дому, городу и типу. Если город не указан, его угадывание
  не объявляется правильным. Неясные намерения не получают искусственного эталона.
- Реальные возможные опечатки: отдельная страта исправленных слов; намерение требует проверки.
- Контролируемые опечатки и опасные пары домов: независимые ожидаемые идентичности, включая отрицательные случаи.

Для каждой страты отдельно считаются автоматическое совпадение, присутствие адреса в выборе,
неверные автоматические ответы, неподходящие варианты, пропуски и fallback v1.
Для эксплуатации измеряются p50/p95, память, диск и работа при отказе поискового сервиса.
Fallback не исправляет неверный уверенный ответ v2.

Настройки сначала отбираются на фиксированной меньшей выборке. Лучшие варианты проходят полный корпус,
ручную проверку новых расхождений и dev. Использованные для исправлений данные больше не называются слепыми.
Новые сообщения могут образовать следующую временную контрольную выборку.

Индекс эксперимента создаётся отдельно на ПК; рабочие псевдонимы не переключаются.
Постоянный OpenSearch на маленьких VDS пока не разворачивается. Если его качество окажется лучше,
отдельно оцениваются размещение и расход ресурсов; существующее решение не выбирается победителем заранее.

## Памятки

Стартовое сообщение обновляется в dev. Новый текст закрепа находится в `docs/pinned-post.md`;
публикация следует после перехода основного бота на новую версию.

## Первые результаты сравнения

Два предварительных прогона выполнены на одних 1 250 случаях: 500 исторических,
453 гипотезах одиночной опечатки и 297 размеченных запросах. Первый прогон содержит
26 профилей, второй — 21 с повторными контрольными профилями; всего 44 разных варианта.
Экспериментальные индексы содержат 1 076 095 документов улиц и не заменяют рабочий индекс.

| Профиль | Историческая подсказка сохранена, из 500 | Подсказка исправления сохранена, из 453 | Конфликты буквальных ограничений в автоматических ответах, из 297 |
| --- | ---: | ---: | ---: |
| Каталог / RapidFuzz | 500 | 381 | 0 |
| Прежний гибрид | 500 | 403 | 0 |
| Самостоятельный OpenSearch без stemming, один edit, префикс 0 | 470 | 414 | 0 |
| Раздельные поля, точные адреса перед fuzzy, без stemming, один edit, группа 0,8 | 500 | 433 | 0 |

Некоторые варианты со stemming нарушили буквальное название улицы: запрос «Батайский 49»
получил улицу Ушинского в городе Батайске. Совпадение города не должно заменять улицу.
Ослабление полноты совпадения до 80% в одном случае отбросило уточнение «Олимпийская деревня».
Такие профили не становятся кандидатами на выпуск лишь из-за числа найденных ответов.

Небольшой прогон не оказался достаточным для выбора. Лучшие профили проверены на 46 611 элементах
прежнего корпуса и 297 размеченных запросах. Ниже «сохранено» включает нужную подсказку среди вариантов.

| Профиль | Исторические подсказки, из 44 083 | Гипотезы исправлений, из 2 528 |
| --- | ---: | ---: |
| Каталог / RapidFuzz | 44 005 | 1 389 |
| Прежний гибрид | 44 005 | 1 423 |
| Раздельные поля, без stemming, один edit, группа 0,8 | 43 968 | 1 371 |
| Раздельные поля, без stemming, AUTO, только верхняя группа | 43 861 | 1 500 |

Универсальный победитель не выбран: AUTO восстанавливает больше гипотез, но теряет часть прежних подсказок.
Среди причин — исходные варианты населённых пунктов и улиц, которые каталог учитывает через aliases,
а экспериментальный индекс пока содержит только в каноническом виде. Также требуется отдельная проверка
Зеленограда, жилых комплексов и оценки одинаковых адресных формулировок с разными неподтверждёнными ID.

Следующая итерация: адресные псевдонимы с привязкой к дому, анализ сокращений и разделителей,
синонимы без stemming, сравнение более широких групп кандидатов. На больших выборках отдельно
разбираются новые автоматические ответы и потери. Результаты не являются оценкой универсальной точности.
Разбор дома и номера улицы в этих прогонах общий; ранжирование native не применяет RapidFuzz.

Прогоны использовали SQLite-артефакт для чтения кодов и локальный HTTP OpenSearch.
Их задержки не сравнивают скорость PostgreSQL с OpenSearch на VDS. Рабочий PostgreSQL проверяется отдельно.
Во время полного прогона зафиксированы исходники; последующее уточнение буквенных диапазонов
проверяется на окончательной сборке отдельно.
