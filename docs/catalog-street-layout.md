# Упорядочивание каталога улиц — 7 ноября 2026

Продолжение [проверки широких запросов](search-prefix-performance.md#пакетное-чтение-каталога-и-пределы-vds).
Изменения `1808667`, `2d3ae97` и `c0c2a32` относятся к физическому хранению PostgreSQL и безопасному запуску обслуживания,
а не к правилам поиска.
Prod и исходная база v1 не изменяются.

## Причина задержки

GIN быстро находит ID улиц, но обычный поиск также читает строки таблицы, проверяет названия
и сортирует кандидатов. В прежней загрузке улицы расположены по населённым пунктам.
Популярное название без города заставляло читать тысячи разнесённых страниц, даже если
запрошенного номера дома в результате нет. Пакетное чтение домов не устранило этот первый этап.

```mermaid
flowchart LR
    G[GIN: ID подходящих улиц] --> H[Чтение строк streets]
    H --> S[Прежний порядок кандидатов]
    S --> B[Проверка точного дома и кодов]
    P[Загрузка рядом одинаковых street_key] -.->|Меньше страниц для чтения| H
```

Новая загрузка сохраняет рядом одинаковые `street_key`. Для уже загруженного dev-каталога
предусмотрено однократное упорядочивание [CLUSTER](https://www.postgresql.org/docs/17/sql-cluster.html)
по временному B-tree, который затем удаляется.
Набор адресов, кодов, ID, связи, определения постоянных индексов и ревизия данных сохраняются.
Итоговый порядок кандидатов по-прежнему задаёт SQL, а не физический порядок строк.

## Что проверено до применения

- Две локальные копии 1 076 094 улиц имеют одинаковую контрольную сумму всех строк.
  В пяти видах запросов совпали кандидаты и порядок. Для широкого названия число затронутых
  буферных страниц уменьшилось примерно с 6,4 тысячи до 955; это не замер доставки VK.
- На временной таблице Германии три широких названия прошли прежний двухсекундный дедлайн:
  первый EXPLAIN ANALYZE — около 697, 161 и 382 мс. Исходная таблица в тех же пробах получала
  `QueryCanceled`. Это диагностическая таблица с локальными буферами; результат отдельно
  перепроверяется на постоянном рабочем каталоге.
- На полной локальной копии БД при PostgreSQL 192 МиБ обслуживание заняло около 10 секунд.
  Контрольная сумма всех строк `streets` и определения постоянных индексов совпали до/после;
  временный индекс удалён, ревизия данных сохранена. Наблюдаемый дополнительный диск —
  около 277 МБ, расчётный запас для этой копии — около 898 МБ сверх аварийного резерва.
- 400 полных ответов рабочего читателя PostgreSQL совпали с файловым эталоном без кеша.
  Проверен отказ в середине транзакции: физический порядок, метаданные и временный индекс
  откатываются. Отдельно проверен возврат прежних приложений при ошибке обслуживания.

Таблицы, EXPLAIN и результаты с запросами остаются в `artifacts/private/street-layout-20261107`.
В публичный отчёт попадают только агрегаты.

## Результат на рабочем dev

[Обслуживание через Actions](https://github.com/omkality/domofomka/actions/runs/42393970020) выполнено
на `2d3ae97`. Первый этап развёртывания этой попытки остановился до изменения каталога:
сервер не смог получить исходники GitHub (`URLError`). Повтор только неуспешного этапа завершился успешно.
Лимиты поиска и памяти не увеличивались; `metadata.street_layout` теперь равен `street-key-v1`.

43 HTTP-запроса и 16 выбранных домов совпали с файловым эталоном по полному JSON, включая
адреса, выбор, коды и причину fallback. Сравнение учитывает представление кортежей v1 как JSON-массивов.
В четырёх широких пробах не было ошибок этапов и `fallback_reason=unavailable`.

| Проба | HTTP без кеша результата, мс | Причина fallback |
| --- | ---: | --- |
| Исходный широкий запрос A | 4 440 | `not_found` |
| Исходный широкий запрос B | 318 | `not_found` |
| Другое распространённое название C | 1 717 | `not_found` |
| Другое распространённое название D | 1 702 | `not_found` |

`not_found` означает завершённый v2 без подходящего дома, после которого допустим прежний поиск.
Воспроизведённые statement timeout устранены. **Первый широкий запрос всё ещё может занимать
несколько секунд**: чтение страниц и первая подготовка словаря не исключены. Один прогон без кеша
результата не является полностью холодным диском и не задаёт SLA. Дальнейшее ускорение не должно
отключать поиск домов без кодов или ослаблять ограничения адреса ради времени.

Две секунды ограничивают отдельный SQL, а `CATALOG_OPERATION_TIMEOUT_SECONDS=5` — весь вызов
читателя каталога; HTTP также включает остальные этапы и допустимый v1. Поэтому несколько
коротких SQL-запросов суммарно могут дать HTTP-время больше двух секунд.

После проверки свободно около 1,22 ГБ диска и 346 МиБ доступной памяти ОС. Это снимок, не
новый лимит. API, бот и прежний PostgreSQL/очередь работают без OOM; нет подмонтированных
исходников, незавершённой транзакции или оставленных данных входа в registry.
VK и DaData в этих HTTP-проверках не вызывались. Prod и Amnezia не менялись.

## Запуск через Actions и ограничения

Ручной запуск **CI and deploy** на ветке `dev`, окружение `dev`, флаг `optimize_catalog=true`.
Обычный push обслуживание не запускает. Prod запрещён и политикой workflow, и проверкой
манифеста на сервере. Тесты и сборка предшествуют обслуживанию, как при обычном выпуске.
Коммит сначала должен быть успешно развёрнут обычным push. Обслуживание использует уже
проверенные активные digest этого коммита и не скачивает на VDS третий комплект образов.

Первый запуск остановила проверка свободного места до изменения каталога: третья сборка
образов оставила примерно на 14 МБ меньше расчётного запаса. Резерв не уменьшался;
исправлен лишний перенос образов, добавлены проверки отсутствия pull, совпадения коммита
и повторного запуска без остановки приложений. Неиспользуемые образы незавершённых релизов
удаляются штатной адресной очисткой приложения; общая очистка Docker не применяется.

До остановки приложений проверяются готовность каталога, версия схемы, ревизия данных и место:
свободными должны оставаться аварийный резерв плюс три текущих размера таблицы с индексами
и ещё 64 МиБ. Операция не создаёт второй полный каталог. Численная оценка консервативна;
расход других служб за время обслуживания из неё не следует.

Останавливаются только API и dev-бот. PostgreSQL, его том и другие контейнеры сохраняются.
В одной транзакции создаётся временный индекс, упорядочивается таблица, индекс удаляется,
обновляется статистика и записывается `metadata.street_layout=street-key-v1`.
Повторный явный запуск с этой отметкой ничего не переписывает и не останавливает приложения.

Параметры в `.env.dev`:

| Параметр | По умолчанию | Назначение |
| --- | ---: | --- |
| `CATALOG_MAINTENANCE_TIMEOUT_SECONDS` | 180 | Таймаут SQL и ограничение процесса обслуживания с небольшим запасом. |
| `CATALOG_MAINTENANCE_LOCK_TIMEOUT_SECONDS` | 5 | Ожидание блокировки таблицы. |
| `CATALOG_MAINTENANCE_MEMORY_MB` | 16 | Память обслуживания PostgreSQL в этой транзакции. |

Обычные `CATALOG_STATEMENT_TIMEOUT_MS=2000` и лимиты памяти рабочих контейнеров не увеличиваются.
Ошибка SQL откатывает транзакцию; ошибка выпуска возвращает прежние приложения.
Успешно завершённое упорядочивание не разворачивается назад при откате приложения:
данные и HTTP-контракт прежние. Прерванный запуск без отметки можно повторить после проверки состояния.

После операции проверяются два исходных широких запроса по HTTP. Ответ, который скрывает
отказ каталога за `fallback_reason=unavailable`, не считается успешной приёмкой. Actions выводит
длительность и попадание в кеш без адресов пользователей и кодов.

[CI кода `c0c2a32`](https://github.com/omkality/domofomka/actions/runs/42395683852) прошёл 729 тестов;
[отдельная приёмка](https://github.com/omkality/domofomka/actions/runs/42396851135) завершилась успешно.
Агрегаты без переписок и кодов: [JSON](catalog-street-layout-summary.json).

Новая сборка каталога уже загружает улицы в нужном порядке и не нуждается в отдельном CLUSTER.
Изменения каталога в будущем могут нарушать физическую группировку; текущий каталог преимущественно
читается, постоянная автоматическая перекластеризация не добавлялась.
