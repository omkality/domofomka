# Тестовое окружение и восстановление запросов

Тестовый бот сообщества **223949627** работает на Германии из `/root/domofomka-dev`.
Рабочий бот в Финляндии использует другое сообщество и отдельное окружение. Эта инструкция относится к ветке `dev`.
Настройки VPN и парольного входа root не меняются.

## Подготовка и запуск

Скопируйте `.env.dev.example` в `.env.dev`, заполните токен тестового сообщества, токен DaData и отдельный пароль PostgreSQL.
Положите исходную `codes.db` в корень проекта, а созданную сборку `serving.db` — в `artifacts/search/`.
Секреты, исходные переписки и базы не входят в Git. Подготовка каталога описана в [документации поиска](search-v2.md).

Для отдельного тестового окружения:

```bash
docker compose --env-file .env.dev -f compose.dev.yml up --build -d queue api vkbot
docker compose --env-file .env.dev -f compose.dev.yml logs --tail=50 vkbot
docker compose --env-file .env.dev -f compose.dev.yml exec -T vkbot uv run --frozen python -m src.vkbot.manage status
```

`compose.dev.yml` задаёт проект `domofomka-dev`, отдельный том PostgreSQL и локальный порт API 18000.
На уже развёрнутой Германии используется тот же проект с основным файлом Compose:

```bash
docker compose -p domofomka-dev --env-file .env.dev -f docker-compose.yml ps
docker compose -p domofomka-dev --env-file .env.dev -f docker-compose.yml exec -T vkbot uv run --frozen python -m src.vkbot.manage status
```

В пределах одного окружения используйте один выбранный набор файлов Compose для всех команд.
В `.env.dev` параметр `DOMOFOMKA_ENV_FILE` должен указывать на `.env.dev`.
Порт PostgreSQL наружу не опубликован. Redis из текущих файлов Compose удалён; очередь и контекст кнопок хранятся в PostgreSQL.
Исходная SQLite остаётся для v1. V2 читает отдельную БД PostgreSQL через роль без прав записи.
Перед запуском нужно загрузить каталог и настроить CATALOG_DATABASE_URL/CATALOG_REVISION:
[схема и публикация](database.md), [проверки переноса](postgres-dev-2026-11-06.md).
Сам OpenSearch на небольшой немецкий VDS не установлен: локальное окружение `compose.search.yml` нужно для сравнений на ПК.
Немецкий бот от ПК не зависит.

Код подключён только для чтения. После изменения Python перезапустите `vkbot` и при необходимости `api`.
При изменении зависимостей пересоберите образы через `up --build -d`.
До запуска обработчиков проверяется `groups.getLongPollServer`: токен должен иметь доступ именно к нужному сообществу.
`EXPECTED_VK_GROUP_ID` должен совпадать с `VK_GROUP_ID`.
Имитация отказов разрешена только при `APP_ENVIRONMENT=development`, `DEV_FAULTS_ENABLED=true` и для тестовой группы 223949627.

## Как сохраняются запросы

1. Long Poll сохраняет события и курсор одной транзакцией, прежде чем получать следующую порцию.
   Если БД недоступна, бот повторяет запись той же порции.
2. Входящий журнал `inbox` хранит сообщения и полученные события нажатий. Уникальные идентификаторы защищают от повторной обработки.
3. Обработчик атомарно записывает готовые действия в исходящий журнал `outbox` и заканчивает планирование.
   `inbox: done` означает подготовленный ответ; доставку показывает **outbox**.
4. Отдельный обработчик отправляет сообщения и редактирует ответы. После временного сбоя повторяет попытку с увеличением задержки:
   примерно от 5 до 300 секунд с небольшим случайным разбросом. Максимум применяется после разброса. Жёсткого числа попыток нет.
5. Внутри диалога задания выполняются последовательно, разные диалоги могут обрабатываться параллельно.
   Интервал запросов VK по умолчанию — 0,4 секунды; это выбранная настройка, а не обещание отсутствия ограничений VK.
   После ошибок авторизации и ограничения частоты действует общая пауза минимум 30 секунд.
6. `messages.send` повторяется с тем же ненулевым `random_id`, связанным с постоянным ID исходящего задания.
   После сохранения результата отправка не повторяется даже при сбое чтения контекста. Редактирование повторяет тот же текст и целевое сообщение.
   Бесконечная гарантия доставки ровно один раз не заявляется: дедупликация зависит и от VK.
7. Задание резервируется на ограниченное время с продлением аренды. После остановки обработчика другой заберёт его по окончании аренды.
   Просроченный владелец не может завершить задание. Блокировка PostgreSQL разрешает один активный процесс бота для сообщества в той же БД.
   Автоматическое переключение между независимыми серверами этим не реализовано.

Постоянные ошибки сохраняются как `failed` и не блокируют диалог бесконечно.
После устранения причины оператор может выполнить `retry-failed`.
Технические ошибки содержат только тип исключения и код VK; исходные сообщения и токены в них не записываются.
Сами события очереди содержат переписки, поэтому доступ к БД и резервным копиям должен быть ограничен.

## Поиск пропущенных сообщений

Сверка истории выполняется при запуске и затем каждые 5 минут.
После успешного полного прохода сохраняется граница; следующий проход начинается от неё с перекрытием 15 минут.
После длительного простоя проверяется весь период с последней успешной границы. Частичный или ошибочный проход её не продвигает.

На первой установке просматриваются предыдущие 24 часа.
Для сообщений до установки очереди применяется эвристика: необработанным считается хвост после последнего исходящего сообщения.
Она не доказывает, что на каждый более ранний запрос был дан подходящий ответ.
Для новых запросов есть журнал очереди и явные ссылки ответов. Постороннее исходящее уведомление само по себе не закрывает новый запрос.

История VK восстанавливает обычные сообщения, но не нажатия, которых бот не получил от VK.
Записанное нажатие можно обработать после таймаута редактирования и перезапуска.
Обычное нажатие по возможности получает пустое подтверждение; предупреждения при повторах ограничены по частоте.
Пока принятое действие не доставлено, любые другие кнопки пользователя подавляются.
После доставки действует общая пауза `ANTI_SPAM_TIME` (по умолчанию 5 секунд); чередование кнопок её не обходит.
Ошибка короткоживущего подтверждения не блокирует доставку кода.
Остаётся окно между получением события процессом и записью в БД; после аварии в нём повтор зависит от Long Poll.
Перекрытие страниц истории уменьшает риск пропуска при активности диалогов, но не создаёт атомарный снимок.

## Управление и проверка отказов

Команды для окружения, запущенного через `compose.dev.yml`:

```bash
docker compose --env-file .env.dev -f compose.dev.yml exec -T vkbot uv run --frozen python -m src.vkbot.manage pause
docker compose --env-file .env.dev -f compose.dev.yml exec -T vkbot uv run --frozen python -m src.vkbot.manage resume
docker compose --env-file .env.dev -f compose.dev.yml exec -T vkbot uv run --frozen python -m src.vkbot.manage retry-failed
```

`pause` прекращает взятие новых заданий, но оставляет сбор событий и сверку истории. Уже начатые запросы могут завершиться.
На Германии подставляйте показанный выше префикс `-p domofomka-dev --env-file .env.dev -f docker-compose.yml`.

```bash
# 1 — один отказ, -1 — постоянный отказ, 0 — выключить.
docker compose --env-file .env.dev -f compose.dev.yml exec -T vkbot uv run --frozen python -m src.vkbot.manage fault vk-edit -1
```

Точки отказа: `api`, `vk-send`, `vk-send-after`, `vk-edit`, `vk-edit-after`.
Суффикс `-after` имитирует потерю подтверждения после принятия запроса VK, но до записи результата в БД.
После проверки выключите все включённые отказы и выполните `resume`.

Проверки: отправка сообщения при остановленном боте с последующим восстановлением;
таймаут редактирования, перезапуск и повтор записанного нажатия;
потеря подтверждения отправки через `vk-send-after 1` с тем же `random_id` без второго сообщения.
Подробные сценарии находятся в [описании доставки](message-delivery.md).

```bash
uv sync --frozen --all-groups
uv run python -m pytest -q
```

Для интеграционных тестов нужен `TEST_QUEUE_DATABASE_URL`, указывающий на отдельную тестовую PostgreSQL.
Без него эти тесты пропускаются. Они используют случайные пространства `group_id` и удаляют только свои данные.

Постоянный том PostgreSQL нельзя удалять через `down -v`: в нём журнал доставки и последовательность `random_id`.
Создавайте резервные копии через `pg_dump`; не запускайте старый снимок одновременно с актуальной очередью.
Очистка завершённых тел заданий сохраняет идентификаторы дедупликации. Для ежедневного резервного копирования есть systemd-таймер.
Параметры, предупреждения и проверка восстановления описаны в [эксплуатации очереди](operations.md).
